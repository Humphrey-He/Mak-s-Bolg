在 Kubernetes 中排障，最怕只盯着应用日志。日志能告诉你代码发生了什么，但它不一定告诉你镜像为什么拉不下来、Pod 为什么调度失败、探针为什么失败、volume 为什么挂载不上。真正高效的排查路径，是把日志、事件和临时调试工具一起用。

对后端开发者来说，`kubectl logs` 负责看应用输出，`kubectl describe` 和 Events 负责看 Kubernetes 对象生命周期，`kubectl debug` 或临时 Pod 负责补齐网络和系统工具。

## 问题场景

一个用户服务从本地迁移到集群后，调用订单服务一直超时。用户服务日志只显示 `connection timeout`，订单服务日志没有请求进来。这个时候继续翻业务日志意义有限，因为请求可能根本没有到达目标 Pod。

正确排查应该从调用链路出发：用户服务 Pod 内 DNS 是否能解析订单 Service，Service 是否有 endpoints，targetPort 是否正确，网络策略是否拦截，订单服务是否 Ready。

## 架构解释

一次集群内服务调用大致经过：

```txt
应用代码
  -> Pod 网络命名空间
  -> CoreDNS 解析 Service 名
  -> Service 虚拟入口
  -> endpoints 后端 Pod
  -> 目标容器端口
```

应用日志只能覆盖最上层。Events 覆盖 Kubernetes 控制面和 kubelet 的动作。临时调试容器则让你进入同一个网络环境，实际执行 `nslookup`、`wget`、`curl` 等命令。

## 核心名词

- `stdout/stderr`：容器日志的标准输出和错误输出，Kubernetes 默认采集这里。
- `Events`：Kubernetes 对资源变化、调度、拉镜像、探针、挂载等行为的记录。
- `ephemeral container`：临时调试容器，可附加到已有 Pod。
- `target container`：调试容器要靠近观察的目标容器。
- `debug Pod`：临时启动的工具 Pod，适合从集群内模拟访问。
- `--previous`：查看上一次崩溃容器的日志。

## 最小示例

先部署一个普通 API：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: registry.example.com/team/api:v1.0.0
          ports:
            - containerPort: 8080
```

从日志开始看：

```bash
kubectl logs deploy/api
kubectl logs -f deploy/api --tail=200
```

如果应用没有明显错误，再看事件：

```bash
kubectl describe deploy api
kubectl describe pod <pod>
kubectl get events --sort-by=.lastTimestamp
```

如果怀疑网络，再启动临时工具：

```bash
kubectl run debug --rm -it --image=busybox -- sh
```

进入后可以执行：

```bash
nslookup api
wget -qO- http://api.default.svc.cluster.local
```

## 高频命令

日志相关：

```bash
kubectl logs <pod>
kubectl logs -f <pod>
kubectl logs deploy/api --tail=200
kubectl logs <pod> -c <container>
kubectl logs <pod> --previous
kubectl logs -n prod -l app=api --tail=100
```

事件相关：

```bash
kubectl describe pod <pod>
kubectl describe deploy api
kubectl get events --sort-by=.lastTimestamp
kubectl get events --field-selector involvedObject.name=<pod>
```

调试容器相关：

```bash
kubectl debug -it <pod> --image=busybox --target=<container>
kubectl debug -it <pod> --image=nicolaka/netshoot --target=<container>
kubectl run debug --rm -it --image=busybox -- sh
kubectl run netshoot --rm -it --image=nicolaka/netshoot -- bash
```

`netshoot` 这类镜像内置了大量网络工具，适合临时排查 DNS、路由、TLS 和 TCP 连接。但生产环境使用前要确认团队安全规范。

## 参数意义

`--tail=200` 表示只看最后 200 行。线上服务日志量很大时，直接拉全量日志既慢又容易淹没重点。

`-f` 表示持续跟随日志。发布、重启或压测时常用它观察错误是否持续出现。

`-l app=api` 表示按 label 选择一组 Pod。Deployment 多副本时，单看一个 Pod 可能漏掉部分副本的问题。

`--previous` 用于查看上一次容器实例日志。容器重启后，当前日志可能只有启动过程，真正的异常栈在 previous 中。

`--target=<container>` 表示临时调试容器要面向哪个容器。多容器 Pod 中尤其重要，因为你希望进入尽量接近业务容器的命名空间。

`--rm -it` 常用于一次性 debug Pod。`--rm` 会在退出后删除 Pod，`-it` 提供交互式终端。

## 常见坑

第一，应用日志没有输出到 stdout/stderr。容器化应用应把日志打到标准输出，由平台统一采集。写到容器本地文件会增加采集复杂度，也容易随容器重建丢失。

第二，只看 Deployment 日志，不看具体 Pod。Deployment 日志会聚合匹配的 Pod，但某些版本、节点或副本特有问题需要定位到具体 Pod。

第三，忽略 Events。镜像拉取、调度失败、探针失败、挂载失败，很多不会出现在应用日志中，却会出现在 Events 中。

第四，在生产 Pod 里安装工具。不可变镜像是基本原则。排查工具应该通过临时容器或临时 Pod 引入，而不是临场修改业务容器。

第五，debug Pod 的命名空间不对。Service DNS、NetworkPolicy、RBAC 都可能和命名空间相关。排查 prod 服务时，debug Pod 最好也启动在相同命名空间。

## 后端开发者检查清单

- [ ] 应用日志输出到 stdout/stderr，不依赖容器内本地文件。
- [ ] CrashLoopBackOff 时使用 `kubectl logs --previous`。
- [ ] 发布问题同时查看 `kubectl rollout status`、Pod 日志和 Events。
- [ ] 网络问题从相同 namespace 的 debug Pod 发起请求。
- [ ] 检查 Service DNS、endpoints、targetPort 和 readinessProbe。
- [ ] 临时调试镜像符合团队安全规范，用完即删。
- [ ] 排查结论写回 runbook，沉淀成下次可复用命令。
