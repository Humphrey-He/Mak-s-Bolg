如果说我前面写 `Claude Code`、`SWE-agent`、`CodeAct` 时，已经越来越强烈地感觉到 coding agent 的关键不只是模型，而是 interface 和 action；那我回头再认真读 Anthropic 的 `Writing Effective Tools for Agents` 时，那个感觉就彻底坐实了。

因为这篇文章在我看来，几乎就是在把一句很多团队嘴上都同意、但做项目时经常做不到的话说透：

> **tool design 不是实现细节，而是 agent 成败分水岭。**

我特别想单独写这篇精读，不是因为里面有多少 checklist，而是因为它帮我把一个很重要的工程判断说得非常清楚：

- 模型不会凭空理解你的系统；
- agent 实际看到的，不是你脑子里的架构图，而是工具名、参数、描述、返回值和错误反馈；
- 工具表面设计得模糊，模型再强也会在动作空间里乱撞；
- 工具表面设计得清晰，很多原本需要“更强模型”的问题，反而会自然收敛。

所以我这篇精读想回答的不是“Anthropic 建议怎么写 tool docstring”这么窄的问题，而是更大的几个问题：

- 为什么 Anthropic 会把工具设计抬到这么高的位置；
- 它到底是在解决“模型不会调工具”，还是在解决“我们给模型暴露的动作空间太差”；
- 这篇文章为什么会自然接到 Claude Code、SWE-agent 和 ACI 那条线；
- 它最终怎样改变我对 agent 工程优先级的判断。

---

## 一、我先抓住这篇文章的总主线

如果整篇文章只允许我带走一句话，我会带走这个：

> **Agent 的很多失败，不是因为模型不知道该做什么，而是因为我们没有把“能做什么”定义清楚。**

我特别喜欢这条主线，因为它把问题一下子从“模型能力”拉回了“动作空间设计”。

以前大家一提 agent 效果不好，很容易先想到：

- prompt 还不够强
- 模型还不够大
- reasoning 还不够深

但 Anthropic 这篇文章其实在反过来提醒我：

```text
也许不是模型不会用工具
而是工具本身就写得让模型很难用
```

我觉得这非常重要。因为它把很多问题从“研究型难题”重新拉回了“工程设计质量”。

---

## 二、为什么我觉得这篇文章是在正面处理 ACI 问题

我前面在 `SWE-agent` 那篇精读里已经写过，ACI 在我看来就是：

> 你到底给模型一个什么样的电脑世界，让它能有效行动。

而 `Writing Effective Tools for Agents` 这篇文章，其实就是在非常具体地回答 ACI 里的一个核心子问题：

> 你到底把工具表面设计成了什么样。

这点我特别有共鸣。

因为很多人谈 ACI 时，容易停留在宏观层：

- 要有文件系统
- 要有 shell
- 要有搜索

但 Anthropic 这篇文章进一步往下钻了一层：

- 工具名称怎么起
- 参数怎么写
- 描述怎么写
- 返回值怎么组织
- 错误信息怎么返回
- 什么信息应该提前暴露

这就让我觉得，它不是在讲一套“tool tips”，而是在讲：

> 动作空间的可用性到底是怎么被具体建出来的。

---

## 三、我为什么越来越相信 tool schema 比很多人以为的更重要

如果让我只挑一个我最认同的点，我会选这个：

> tool schema 本身就是 prompt 的一部分，甚至很多时候比总 prompt 更影响 agent 行为。

这点我现在几乎是越来越坚定的。

因为从模型视角看，它真正拿到的不是“我们设计得很优雅的一套系统”，而是一些非常具体的表面：

- 工具叫啥
- 参数名叫啥
- 参数之间怎么约束
- description 怎么写
- 返回值是什么结构

如果这些东西含糊，模型就只能猜。

而一旦开始猜，错误就会迅速放大：

- 选错工具
- 传错参数
- 误解返回值
- 调用链路开始漂

所以我现在越来越愿意把 schema 理解成：

> agent 与系统动作空间之间的正式契约。

这已经不是“文档要不要写详细一点”的问题了，而是系统动作边界清不清楚的问题。

---

## 四、我怎么理解这篇文章为什么如此强调 description

很多人一提 tool description，会觉得这是个很软的问题，好像只是“写得友好一点”。

但我自己完全不这么看。

在我眼里，description 真正承担的是三层功能：

### 4.1 它在告诉模型“什么时候该用这个工具”

如果没有这一层，模型只能基于名字猜意图。

而很多真实工具名在业务环境里并不天然清楚。比如：

- `run_job`
- `submit_task`
- `sync_doc`
- `publish_record`

这些名字如果没有上下文，模型很容易误判。

### 4.2 它在告诉模型“什么时候不该用这个工具”

这点我觉得尤其重要。

一个好 description 不只是告诉模型“能做什么”，还应该隐含地缩小动作空间：

- 适用边界
- 非适用边界
- 风险提示
- 前置条件

这能显著减少乱调用。

### 4.3 它在给模型建立动作预期

也就是：

- 调完会拿到什么
- 返回值适合做什么
- 失败时会怎样

这会直接影响后续推理是否稳定。

所以我现在越来越把 description 看成“行为指导语”，而不是普通文档注释。

---

## 五、为什么返回值格式会直接决定 agent 上限

这也是我读 Anthropic 这篇文章时特别有共鸣的一点。

很多系统把注意力都放在“怎么调用工具”，却低估了“工具返回什么样的数据给模型”。

我越来越觉得，返回值设计很多时候和输入 schema 一样重要。

因为如果返回值：

- 太乱
- 太长
- 太口语化
- 关键信息被噪声淹没

那模型下一步还是得猜。

我会把一个好的返回值理解成具备这些特征：

- 结构化
- 可定位关键字段
- 错误和正常结果有明显区分
- 对后续动作决策有帮助

这点其实和 `CRAG`、`Self-RAG` 那条线也能扣上。因为说到底，agent 要靠反馈闭环工作，而反馈如果返回得不对，闭环就会很弱。

所以我现在越来越愿意把“返回值设计”当成 action surface 的一部分，而不是后端实现顺手带出来的副产物。

---

## 六、为什么我觉得这篇文章真正想解决的是“动作空间噪声”

如果我要把 Anthropic 这篇文章抽象成一句更偏工程的话，我会说：

> 它想解决的，不只是工具可不可用，而是 agent 所面对的动作空间噪声太大。

这个“噪声”非常具体：

- 工具名称有歧义
- 参数设计不自然
- 描述太短或太泛
- 错误反馈不可诊断
- 返回格式不利于下一步推理

一旦这些噪声存在，模型就很容易把错误当正确路径继续往下走。

我为什么特别在意这个问题？因为我现在做 agent 系统时越来越能感觉到：

> 很多所谓“模型不稳定”，本质上是动作空间不稳定。

如果动作空间噪声很大，agent 的行为就算偶尔对了，也很难稳。

所以我非常认同 Anthropic 这篇文章的核心气质：它不是去追求更神奇的自主性，而是在主动降低 agent 的行动噪声。

---

## 七、这篇文章为什么会自然接到 Claude Code 和 SWE-agent

我现在回头看，会觉得这篇文章几乎天然就是 `Claude Code` 和 `SWE-agent` 那条线的下游补充。

### 7.1 对 Claude Code 来说，工具表面就是产品交互的一部分

Claude Code 之所以让我觉得像 coding agent 产品形态，很大原因是它并不是只会聊天，而是会：

- 读文件
- 搜代码
- 改文件
- 跑命令

这些动作一旦存在，工具设计问题就会立刻变成主问题。

所以我现在看 Claude Code，不会只看“它用了什么模型”，我也会想：

- 它的工具抽象一定花了很多心思
- 它怎么减少工具误用
- 它怎么把命令和文件系统反馈组织给模型

而这正是 Anthropic 这篇文章在讲的东西。

### 7.2 对 SWE-agent 来说，tool design 就是 ACI 的细粒度落点

`SWE-agent` 强调 ACI，我完全认同。

但 ACI 如果要真正落地，最后一定会落到：

- 每个动作怎么暴露
- 工具面怎么命名
- 参数怎么约束
- 返回值怎么组织

这时候 `Writing Effective Tools for Agents` 就不是旁支，而是 ACI 的具体施工手册。

所以我现在会觉得，这篇文章和 `SWE-agent` 根本不是两条平行线，它们是同一条线的不同层级：

- `SWE-agent` 讲的是为什么 ACI 重要
- `Writing Effective Tools` 讲的是 ACI 里工具这一层怎么做

---

## 八、为什么这篇文章改变了我对 agent 工程优先级的排序

这是我最想说的一点。

以前很多团队做 agent，优先级容易长这样：

```text
先试 prompt
→ 再换模型
→ 再加规划
→ 最后工具随便补补
```

但我现在越来越倾向于另一种顺序：

```text
先把工具面设计清楚
→ 让模型有明确动作空间
→ 再去看 prompt、planning、memory 要不要继续加复杂度
```

这不是说 prompt 和 planning 不重要，而是说：

> 如果动作空间本身就很乱，上层的聪明只会变成更高成本的乱撞。

我觉得 Anthropic 这篇文章给我的最大收获，就是它让我在优先级上更克制，也更扎实。

以后只要系统已经涉及多工具动作，我会更早去检查这些东西：

- 工具名称是否唯一且清楚
- schema 是否自然
- description 是否减少歧义
- 返回值是否利于下一步推理
- 风险工具是否有确认机制

这些检查以前我可能会放在实现后面，现在我会更早做。

---

## 九、我把这篇文章带回自己系统里，会留下哪些方法论

如果不复述 Anthropic 的原文建议，只说我会真正带回工程里的东西，我会留下下面几条。

### 9.1 tool design 要进核心架构，不要留在实现边角

工具表面不是顺手一写的 wrapper，而是 agent runtime 的核心组成。

### 9.2 schema 是契约，不是补充说明

如果 schema 写不清楚，模型行为一定不稳。

### 9.3 description 不是注释，而是动作指导语

它要帮助模型判断：

- 什么时候用
- 什么时候别用
- 调完能得到什么

### 9.4 返回值必须为“下一步动作”服务

不是给人看舒服就够，而是要对 agent 的后续决策有帮助。

### 9.5 高风险工具必须有显式边界

这点我越来越重视。因为 agent 一旦真的有行动能力，安全边界就不是附属品，而是基础设施。

---

## 十、结语：我为什么越来越把 tool design 看成分水岭

对我来说，`Writing Effective Tools for Agents` 最值钱的地方，不是它给了我一份工具设计 checklist，而是它把一个非常重要的事实说透了：

> **agent 的很多失败，不发生在“想”这一层，而发生在“能做什么、怎么做、反馈怎么回来”这一层。**

如果要把这篇文章留成一句我会长期带着走的话，那大概就是：

> **当系统从 demo 走向工程，tool design 往往比继续打磨总 prompt 更值钱。**

这也是为什么我越来越把它看成 agent 成败分水岭。因为它最终改变的，不只是写几个工具的方式，而是我对整个系统优先级的排序：

- 先把动作空间定义清楚
- 再让模型在这个空间里行动
- 然后再去追求更复杂的自治能力

我很喜欢这种顺序。因为它让我在追新框架、新模型、新策略时，不会忘记最朴素的一件事：**如果工具面没设计好，agent 再聪明也很难稳。**
