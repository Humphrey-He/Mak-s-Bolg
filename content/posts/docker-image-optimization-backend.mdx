## 这篇解决什么问题

后端服务容器化之后，第一版镜像通常都能跑，但不一定适合长期使用。常见问题包括：

- 镜像几百 MB 甚至数 GB，CI 推送慢，节点拉取慢。
- 改一行代码也重新下载所有依赖，构建反馈很慢。
- `.env`、私钥、测试文件、数据库备份进入镜像。
- 生产镜像里保留编译器、包管理器、源码和调试工具。
- 容器默认 root 运行，挂载目录权限和安全边界不清晰。
- 盲目换 Alpine，结果遇到 glibc、证书、时区、DNS 或 cgo 兼容问题。
- 镜像没有 SBOM、漏洞扫描和 digest 记录，无法审计和回滚。

镜像优化不是单纯追求越小越好，而是在**体积、缓存、安全、可复现、可运维**之间做取舍。对后端开发者来说，目标是让镜像只包含运行服务需要的内容，并且构建过程稳定、可重复、密钥不泄漏、运行权限最小化。

## 优化目标

镜像优化可以拆成四类目标：

```txt
体积：减少无关文件、构建工具链和缓存
缓存：让依赖下载和编译缓存可复用
安全：密钥不进镜像，非 root 运行，最小权限
治理：镜像可扫描、可审计、可签名、可按 digest 部署
```

工程上的优先级建议是：

1. 使用 `.dockerignore` 减小 build context。
2. 调整 `COPY` 顺序，提高依赖层缓存命中率。
3. 使用多阶段构建，运行镜像不带构建工具链。
4. 只复制必要产物，不复制源码、测试、文档、缓存。
5. 清理包管理器缓存。
6. 使用 slim、distroless、scratch 等更小 runtime。
7. 用 `docker history` 或 `dive` 定位大层。
8. 最后再考虑二进制裁剪等更激进手段。

不建议优先使用 UPX 压缩后端二进制。它可能影响启动速度、调试、漏洞扫描和运行时兼容性。

## Build context 与 .dockerignore

`docker build -t my-api:local .` 最后的 `.` 是 build context。Dockerfile 只能复制 build context 里的文件。上下文越大，构建越慢，也越容易误把密钥、日志、缓存、测试数据带进镜像。

推荐模板：

```dockerignore
.git
.gitignore

.env
.env.*
!.env.example

node_modules
dist
build
coverage

tmp
.cache
*.log

.idea
.vscode

__pycache__
.pytest_cache
.mypy_cache

target
bin
obj

*.pem
*.key
*.crt
*.p12
*.sqlite
*.db

docker-compose*.yml
compose*.yaml
```

但 `.dockerignore` 不是越多越好。如果 Dockerfile 需要 `COPY` 某个文件，它就不能被忽略。例如某些项目需要复制 migration 文件、config schema、CA 证书或预构建产物。

排查构建上下文问题：

```bash
docker build --no-cache --progress=plain -t api:test .
```

如果出现：

```txt
COPY failed: file not found in build context
```

优先检查：

- 文件是否在当前 build context 下。
- 是否被 `.dockerignore` 排除了。
- `docker build` 的 context 路径是否写错。
- Dockerfile 是否来自另一个目录。

## Layer cache 与 BuildKit cache mount

Docker layer cache 依赖指令和文件内容。依赖文件变化频率通常低于源码，所以应先复制依赖描述文件，安装依赖，再复制业务代码。

BuildKit cache mount 解决的是另一类问题：包管理器下载缓存和编译缓存复用。

两者不是替代关系，而是互补关系：

```txt
Layer cache -> 复用 Dockerfile 指令层
BuildKit cache mount -> 复用依赖下载目录和编译缓存
```

Go 示例：

```dockerfile
# syntax=docker/dockerfile:1.7

FROM golang:1.24 AS builder

WORKDIR /src

COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .

RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/api \
    ./cmd/server
```

Node.js 示例：

```dockerfile
RUN --mount=type=cache,target=/root/.npm \
    npm ci
```

pnpm 示例：

```dockerfile
RUN corepack enable
RUN --mount=type=cache,target=/root/.local/share/pnpm/store \
    pnpm install --frozen-lockfile
```

## 多阶段构建与生产 Go 模板

一个更接近生产的 Go 后端镜像模板：

```dockerfile
# syntax=docker/dockerfile:1.7

ARG GO_VERSION=1.24
ARG VERSION=dev
ARG GIT_COMMIT=unknown

FROM golang:${GO_VERSION} AS builder

WORKDIR /src

COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .

RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build \
    -trimpath \
    -ldflags="-s -w -X main.version=${VERSION} -X main.commit=${GIT_COMMIT}" \
    -o /out/api \
    ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot

ARG VERSION=dev
ARG GIT_COMMIT=unknown

LABEL org.opencontainers.image.title="backend-api" \
      org.opencontainers.image.version="${VERSION}" \
      org.opencontainers.image.revision="${GIT_COMMIT}"

WORKDIR /app
COPY --from=builder /out/api /app/api

EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/app/api"]
```

构建：

```bash
docker build \
  --build-arg VERSION=v1.2.3 \
  --build-arg GIT_COMMIT=$(git rev-parse HEAD) \
  -t registry.example.com/team/backend-api:v1.2.3 \
  -t registry.example.com/team/backend-api:git-$(git rev-parse --short HEAD) \
  .
```

查看层：

```bash
docker history registry.example.com/team/backend-api:v1.2.3
```

扫描：

```bash
trivy image registry.example.com/team/backend-api:v1.2.3
```

## Runtime 镜像取舍

镜像优化不是把基础镜像一律换成 Alpine，而是根据运行时依赖选择最小可用镜像。

| Runtime 镜像 | 优点 | 风险 / 代价 | 适合场景 |
| --- | --- | --- | --- |
| `scratch` | 极小，无 shell | 无 CA、无时区、无 shell、排障困难 | 完全静态二进制 |
| `distroless` | 小、安全、有非 root 变体 | 无 shell，排障依赖外部工具 | 生产 Go / Java / Node 服务 |
| `alpine` | 小，有包管理器 | musl 兼容性问题，部分依赖异常 | 简单服务、明确兼容 musl |
| `debian-slim` | 兼容性好 | 体积比 Alpine 大 | 需要 glibc、CA、tzdata、排障工具 |
| `ubuntu` | 生态完整 | 体积较大 | 特殊依赖或内部标准镜像 |

这些场景不建议盲目 Alpine：

- 依赖 glibc 的动态库。
- 使用 cgo。
- 需要字体、图像处理、PDF、浏览器自动化。
- 需要复杂 DNS、证书或时区行为。
- 线上需要进入容器临时排障。

镜像优化有一条底线：不能为了小而牺牲可运维性。HTTPS 客户端可能需要 CA 证书；涉及时区展示的服务可能需要 `tzdata`；依赖动态库的服务需要保留运行库。

推荐策略是：生产镜像保持精简，同时维护 debug tag，或使用 `kubectl debug`、ephemeral container、`netshoot` 这类外部排障方式。

## 构建期密钥：secret mount

`.env`、私钥、测试数据、数据库备份应该被 `.dockerignore` 排除。但真实后端工程经常需要构建期访问私有依赖：

- Go 私有 module。
- npm 私有包。
- Maven 私有仓库。
- pip 私有源。
- Git 私有仓库。

不推荐：

```dockerfile
ARG TOKEN
RUN git config --global url."https://${TOKEN}@github.com/".insteadOf "https://github.com/"
```

推荐 BuildKit secret：

```dockerfile
# syntax=docker/dockerfile:1.7

RUN --mount=type=secret,id=netrc,target=/root/.netrc \
    go mod download
```

构建：

```bash
docker build \
  --secret id=netrc,src=$HOME/.netrc \
  -t my-api:local .
```

npm 示例：

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
```

构建：

```bash
docker build \
  --secret id=npmrc,src=$HOME/.npmrc \
  -t node-api:local .
```

原则：

- 密钥不要 `COPY` 进镜像。
- 密钥不要写入 `ARG` / `ENV`。
- 密钥不要出现在 `docker history`。
- 构建期临时密钥优先使用 BuildKit secret mount。

## 非 root 与最小权限运行

`USER app` 会让后端进程以普通用户运行。但生产镜像还要考虑 UID/GID、目录权限和只读文件系统。

如果应用需要写目录：

```dockerfile
RUN mkdir -p /app/logs /app/uploads \
    && chown -R app:app /app/logs /app/uploads
USER app
```

更推荐的方向是：

- 日志输出到 stdout/stderr。
- 上传文件写对象存储。
- 本地临时文件写 `/tmp`。
- 容器根文件系统尽量只读。

Compose 层面的最小权限示例：

```yaml
services:
  api:
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
```

这会让文章中的“非 root”从一个 Dockerfile 指令升级为完整的最小权限运行思路。

## 供应链安全：SBOM、扫描、签名、digest

镜像安全不只是不以 root 运行，还包括镜像内容可追踪、依赖可审计、漏洞可发现、发布物不可被静默替换。

| 能力 | 作用 |
| --- | --- |
| Vulnerability Scan | 扫描基础镜像、系统包、语言依赖漏洞 |
| SBOM | 生成镜像软件物料清单，便于审计 |
| Image Signing | 证明镜像来源可信 |
| Digest Pinning | 锁定部署内容，避免 tag 漂移 |
| Provenance | 记录镜像由哪个源码、CI、参数构建 |

常用命令：

```bash
trivy image my-api:local
docker scout cves my-api:local
syft my-api:local -o spdx-json > sbom.json
cosign sign registry.example.com/team/my-api@sha256:<digest>
```

生产发布建议使用明确 tag，并记录最终 digest。tag 方便人理解，digest 才是内容身份。

## 高频命令

```bash
docker build -t my-api:local .
docker build --no-cache --progress=plain -t my-api:test .
docker images my-api
docker history my-api:local
docker image inspect my-api:local
docker system df
docker image prune
trivy image my-api:local
```

`docker history` 可以观察镜像层大小，定位是哪条 Dockerfile 指令引入了大文件。`docker system df` 用来看本机镜像、容器、缓存占用。`image prune` 会清理悬空镜像，但不要在不理解环境的生产机器上随手执行。

## 问题导向排障

### 镜像变大怎么排查

```bash
docker images
docker history my-api:local
docker system df
```

重点看：

- 是否 `COPY` 了 `.git`、`node_modules`、测试数据。
- 是否最终镜像仍然基于 builder。
- 是否 apt/apk 缓存未清理。
- 是否把编译产物和源码都复制进运行镜像。
- 是否没有使用 `.dockerignore`。

### 构建突然变慢怎么排查

```bash
docker build --progress=plain -t my-api:local .
```

重点看：

- 哪一层 cache miss。
- `go.mod` / `package-lock` 是否频繁变化。
- `COPY . .` 是否放太早。
- CI 是否每次都是冷缓存。
- 是否没有使用 BuildKit cache mount。

### 优化后服务不能运行

```bash
docker run --rm my-api:local
docker logs <container>
docker inspect <container>
```

重点看：

- distroless / scratch 是否缺少 CA 证书或动态库。
- 应用是否依赖时区、字体、浏览器、图像处理库。
- 非 root 用户是否有目录写权限。
- 服务是否监听 `0.0.0.0`。
- 健康检查和集成测试是否覆盖启动路径。

## 后端开发者检查清单

- [ ] 是否使用多阶段构建。
- [ ] 是否使用 `.dockerignore` 控制 build context。
- [ ] 是否先复制依赖描述文件，再安装依赖，再复制业务代码。
- [ ] 是否使用 BuildKit cache mount 加速依赖下载和编译。
- [ ] 是否避免把密钥放进 `COPY`、`ARG`、`ENV` 或镜像层。
- [ ] 是否使用 BuildKit secret mount 处理私有依赖。
- [ ] 最终镜像是否不包含源码、测试数据、编译器和包管理器。
- [ ] 是否根据依赖选择合适 runtime，而不是盲目 Alpine。
- [ ] 是否使用非 root 用户运行。
- [ ] 是否处理了写目录权限。
- [ ] 是否考虑只读文件系统、drop capabilities、no-new-privileges。
- [ ] 是否使用明确 tag，并在生产记录 digest。
- [ ] 是否生成 SBOM、做漏洞扫描。
- [ ] 是否通过 `docker history` / `dive` 检查大层来源。
- [ ] 优化后是否跑过启动、接口、健康检查和集成测试。
