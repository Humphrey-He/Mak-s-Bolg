## 这篇解决什么问题

后端服务在不同环境里通常只有配置不同：数据库地址、Redis 地址、日志级别、开关、第三方接口地址、Token 和密码。如果把这些内容写进镜像，就会出现一个镜像只能跑一个环境、配置变更必须重新构建、密钥泄漏难以追踪等问题。

Kubernetes 用 ConfigMap 管理普通配置，用 Secret 管理敏感配置。它们让镜像保持环境无关，让部署时再注入配置。后端开发者需要理解的重点不是“怎么创建对象”，而是配置进入进程的路径、变更是否自动生效、哪些信息不能明文扩散。

## 架构位置

```txt
镜像：只包含代码、运行时和默认启动命令
Deployment：声明如何运行服务
ConfigMap：普通配置，如 APP_ENV、LOG_LEVEL
Secret：敏感配置，如 DB_PASSWORD、JWT_SECRET
Pod：通过环境变量或挂载文件把配置交给进程
```

配置对象不直接改变应用行为，只有被 Pod 引用后才会进入容器。应用读取环境变量、读取配置文件，或者启动时从固定路径加载证书，都是后端代码和部署配置共同约定的结果。

## 核心名词

- ConfigMap：非敏感键值配置或配置文件。
- Secret：敏感键值、证书、镜像仓库凭据等。
- env：逐个注入环境变量。
- envFrom：批量注入一个 ConfigMap 或 Secret。
- volumeMounts：把配置挂载成文件。
- key：配置项名称。
- optional：引用不存在时是否允许 Pod 继续启动。
- base64：Secret YAML 中常见的编码形式，不等于加密。

## 最小可运行示例

创建普通配置和敏感配置：

```bash
kubectl create configmap api-config \
  --from-literal=APP_ENV=prod \
  --from-literal=LOG_LEVEL=info

kubectl create secret generic api-secret \
  --from-literal=DB_PASSWORD='change-me'
```

在 Deployment 中按 key 注入：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: registry.example.com/team/api:v1.0.0
          env:
            - name: APP_ENV
              valueFrom:
                configMapKeyRef:
                  name: api-config
                  key: APP_ENV
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: api-secret
                  key: DB_PASSWORD
```

如果应用需要配置文件，可以挂载成文件：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-file-config
data:
  application.yaml: |
    server:
      port: 8080
    feature:
      newCheckout: true
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: registry.example.com/team/api:v1.0.0
          volumeMounts:
            - name: config
              mountPath: /app/config/application.yaml
              subPath: application.yaml
      volumes:
        - name: config
          configMap:
            name: api-file-config
```

## 高频命令

```bash
kubectl get configmap
kubectl get secret
kubectl describe configmap api-config
kubectl get secret api-secret -o yaml
kubectl create configmap api-config --from-file=application.yaml
kubectl create secret generic api-secret --from-literal=DB_PASSWORD=secret
kubectl rollout restart deploy/api
```

`describe configmap` 可以看普通配置内容，但 `describe secret` 不会直接显示敏感值。`get secret -o yaml` 会看到 base64 后的值，仍然应当按敏感数据处理。配置变更后，如果应用只在启动时读取环境变量，通常需要 `rollout restart` 重启 Pod。

## 参数意义

`configMapKeyRef` 表示从指定 ConfigMap 中取一个 key 注入为环境变量。适合少量关键配置，优点是显式，缺点是字段较多。

`secretKeyRef` 用法类似，但来源是 Secret。它不会自动让信息绝对安全，只是避免以普通 ConfigMap 方式暴露。生产环境还要配合 RBAC、etcd 加密、审计和最小权限。

`envFrom` 可以批量注入：

```yaml
envFrom:
  - configMapRef:
      name: api-config
  - secretRef:
      name: api-secret
```

它很方便，但也容易把不该暴露给进程的 key 全部塞进环境变量。团队中建议对核心服务使用显式 `env`，对工具服务或本地环境再考虑 `envFrom`。

`subPath` 让单个配置文件挂载到指定路径，但 ConfigMap 更新后，使用 subPath 的文件通常不会自动刷新。依赖热更新的应用要谨慎选择挂载方式。

## 常见问题

配置改了但服务没变化，多数是应用启动时读取环境变量，没有重新启动。执行 `kubectl rollout restart deploy/api`，并确认新 Pod 已经创建。

Pod 报 `CreateContainerConfigError`，常见原因是引用的 ConfigMap、Secret 或 key 不存在。先看 `kubectl describe pod <pod>` 里的 Events。

Secret 被误认为“加密存储”。YAML 里的 base64 只是编码，任何有读取权限的人都能解码。真正的保护来自权限控制、存储加密和密钥轮换流程。

把整份 `.env` 直接塞进 Secret 很省事，但容易混入无用配置和过期密钥。建议按服务边界拆分，命名清楚，并定期清理。

## 后端开发者检查清单

- [ ] 镜像中不包含环境专属配置和密钥。
- [ ] 普通配置进 ConfigMap，密码、Token、证书进 Secret。
- [ ] Deployment 引用的 key 名与实际对象一致。
- [ ] 配置变更后知道应用是否需要重启。
- [ ] Secret 读取权限按 namespace 和 ServiceAccount 收敛。
- [ ] 不在日志中打印完整环境变量和敏感配置。
- [ ] 证书、密码和 Token 有轮换计划。
