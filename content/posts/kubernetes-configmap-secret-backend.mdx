## 为什么配置不能写进镜像

后端服务在不同环境里通常只有配置不同：数据库地址、Redis 地址、日志级别、开关、第三方接口地址、Token 和密码。如果把这些内容写进镜像，就会出现一个镜像只能跑一个环境、配置变更必须重新构建、密钥泄漏难以追踪等问题。

Kubernetes 用 ConfigMap 管理普通配置，用 Secret 管理敏感配置。它们让镜像保持环境无关，让部署时再注入配置。

后端开发者需要理解的重点不是“怎么创建对象”，而是：

- 配置通过什么路径进入进程？
- 更新后是否会自动生效？
- 哪些信息不能明文进入 Git？
- Secret 是否真的加密？
- 配置变更如何触发 rollout？
- 密钥如何轮换、审计和最小授权？

## 职责边界

```txt
镜像：只包含代码、运行时和默认启动命令
Deployment：声明如何运行服务
ConfigMap：普通配置，如 APP_ENV、LOG_LEVEL、DB_HOST
Secret：敏感配置，如 DB_PASSWORD、JWT_SECRET、TLS key
Pod：通过环境变量或挂载文件把配置交给进程
```

配置对象不直接改变应用行为，只有被 Pod 引用后才会进入容器。应用读取环境变量、读取配置文件，或者启动时从固定路径加载证书，都是后端代码和部署配置共同约定的结果。

## 注入方式对比

| 注入方式 | 优点 | 缺点 | 更新后是否自动进入进程 |
| --- | --- | --- | --- |
| `env` | 显式、可控 | 字段多 | 不会，需要重启 Pod |
| `envFrom` | 方便批量注入 | 容易暴露过多 key、命名冲突 | 不会，需要重启 Pod |
| ConfigMap volume | 适合配置文件 | 应用需监听文件变化 | 文件可更新，但应用未必 reload |
| Secret volume | 适合证书、密钥文件 | 权限和挂载路径要管理 | 文件可更新，但应用未必 reload |
| `subPath` | 单文件挂载到指定路径 | 更新通常不会自动刷新 | 基本不适合热更新 |

核心结论：

```txt
环境变量适合启动时配置；
volume 适合配置文件和证书；
subPath 适合固定文件路径兼容，但不适合依赖动态更新。
```

## ConfigMap 与 Secret 示例

普通配置：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
  labels:
    app.kubernetes.io/name: api
data:
  APP_ENV: "prod"
  LOG_LEVEL: "info"
  DB_HOST: "mysql.prod.svc.cluster.local"
  DB_PORT: "3306"
```

敏感配置可以用 `stringData` 降低手写 base64 错误：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: api-secret
  labels:
    app.kubernetes.io/name: api
type: Opaque
stringData:
  DB_PASSWORD: "change-me"
  JWT_SECRET: "change-me-too"
```

`data` 需要 base64；`stringData` 可以写明文，由 API Server 转换。但无论 `data` 还是 `stringData`，都不要把真实生产密钥提交到 Git。

Deployment 中显式注入关键配置：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: api
      annotations:
        checksum/config: "replace-with-config-hash"
    spec:
      containers:
        - name: api
          image: registry.example.com/team/api:v1.0.0
          env:
            - name: APP_ENV
              valueFrom:
                configMapKeyRef:
                  name: api-config
                  key: APP_ENV
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: api-config
                  key: LOG_LEVEL
            - name: DB_HOST
              valueFrom:
                configMapKeyRef:
                  name: api-config
                  key: DB_HOST
            - name: DB_PORT
              valueFrom:
                configMapKeyRef:
                  name: api-config
                  key: DB_PORT
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: api-secret
                  key: DB_PASSWORD
```

关键服务建议用显式 `env`，避免 `envFrom` 把多余 key 全量注入。

## 配置文件挂载与 subPath

推荐挂载目录：

```yaml
volumeMounts:
  - name: config
    mountPath: /app/config
    readOnly: true
volumes:
  - name: config
    configMap:
      name: api-file-config
```

应用读取：

```txt
/app/config/application.yaml
```

如果必须挂载单文件到固定路径，再用：

```yaml
volumeMounts:
  - name: config
    mountPath: /app/config/application.yaml
    subPath: application.yaml
    readOnly: true
```

但要记住：`subPath` 通常不会跟随 ConfigMap 更新，适合固定启动配置，不适合热更新配置。

## 更新传播机制

配置更新语义很容易误解：

```txt
通过 env / envFrom 注入的配置，在容器启动时固化为进程环境变量。
ConfigMap/Secret 后续更新不会改变已运行进程环境。

通过 volume 挂载的 ConfigMap/Secret，Kubelet 会周期性同步文件内容，但存在延迟。
应用是否生效取决于是否监听文件变化或重新读取配置。

通过 subPath 挂载的单个文件通常不会收到后续更新。
```

Kubernetes 原生不会因为 ConfigMap 内容变化自动 rollout Deployment。如果配置变更必须重启应用，需要在发布系统中显式触发 rollout。

方式一：手动重启。

```bash
kubectl rollout restart deploy/api
kubectl rollout status deploy/api
```

方式二：Pod template annotation 中加入配置 hash。Helm 常用：

```yaml
spec:
  template:
    metadata:
      annotations:
        checksum/config: "<sha256-of-config>"
```

方式三：Kustomize 使用 `configMapGenerator` / `secretGenerator`，让对象名随内容变化。

方式四：使用 reloader controller，例如：

```txt
stakater/reloader
```

## Secret 类型与镜像拉取凭据

常见 Secret 类型：

| 类型 | 用途 |
| --- | --- |
| `Opaque` | 普通键值密钥 |
| `kubernetes.io/dockerconfigjson` | 镜像仓库拉取凭据 |
| `kubernetes.io/tls` | TLS 证书和私钥 |
| `kubernetes.io/service-account-token` | ServiceAccount token，现代集群不建议手动长期创建 |

TLS Secret：

```bash
kubectl create secret tls api-tls \
  --cert=tls.crt \
  --key=tls.key
```

镜像拉取：

```bash
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=xxx \
  --docker-password=xxx
```

Deployment：

```yaml
imagePullSecrets:
  - name: regcred
```

## Secret 安全模型

Secret 的 base64 不是加密。

更准确的模型是：

```txt
1. Secret 在 API 层是 Kubernetes 对象。
2. 有权限 get/list/watch Secret 的用户或控制器可以读取明文。
3. Secret 默认存储在 etcd 中，是否加密取决于集群配置。
4. Secret 被挂载到 Pod 后，Pod 内进程可以读取。
5. Secret 进入环境变量后，可能被进程 dump、错误日志、调试命令泄漏。
```

生产要求：

- 开启 etcd encryption at rest。
- 使用 RBAC 最小权限。
- 禁止普通开发者 list 全 namespace secrets。
- 使用 External Secrets / CSI Driver 接入云 KMS 或 Vault。
- 定期轮换密钥。
- 审计 Secret 访问。
- 避免在日志、异常、metrics 中暴露环境变量。

Secret 解码检查：

```bash
kubectl get secret api-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
```

这条命令会输出敏感值，生产环境谨慎使用，避免进入 shell history 或日志。

## External Secrets、Sealed Secrets 与 GitOps

生产密钥不应以明文 YAML 进入 Git。

常见方案：

```txt
External Secrets Operator -> 从云厂商 Secret Manager / Vault 同步 Secret
Secrets Store CSI Driver  -> 运行时挂载外部密钥
Sealed Secrets            -> 加密后的 Secret 可以进入 Git，由集群内控制器解密
Vault Agent / Sidecar     -> 注入或刷新密钥
```

GitOps 管理建议：

- 普通 ConfigMap 可以进入 Git。
- 生产 Secret 不应明文进入 Git。
- 不同环境用 namespace、overlay 或 values 分离。
- 配置变更要可审计，可回滚。
- 配置 drift 要能被 GitOps 工具发现。

## 命名、拆分、版本化和 immutable

推荐命名：

```txt
api-config
api-secret
api-db-secret
api-tls
api-feature-flags
```

拆分策略：

- 按服务拆分，不要多个服务共用一个巨大 Secret。
- 按生命周期拆分，频繁变化的配置和稳定配置分开。
- 按权限拆分，数据库密码、JWT 密钥、第三方 Token 分开。
- 按环境分开 namespace 或使用 GitOps overlay。

避免：

```txt
global-secret
common-config
all-env
prod-secret
```

有些配置不应该被原地改动，可以使用：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config-v1
immutable: true
data:
  APP_ENV: prod
  LOG_LEVEL: info
```

价值：

- 防止误改运行中配置。
- 降低 kubelet watch 压力。
- 强制配置变更走新对象 + rollout 流程。

核心生产配置可以考虑不可变配置对象，用版本化命名管理。

## 配置校验与大小边界

应用启动时应校验必需配置。缺少关键配置应 fast fail，错误信息应明确配置名，但不要打印敏感值。

示例：

```txt
missing required config: DB_HOST
invalid config: LOG_LEVEL must be one of debug, info, warn, error
missing required secret: DB_PASSWORD
```

ConfigMap / Secret 不是大文件存储。单个对象大小有限，不适合存放大配置、大证书包、大模型文件、数据库备份或二进制资源。

如果需要二进制：

```txt
Secret 和 ConfigMap 都支持 binaryData，但仍不适合大文件。
```

大文件建议使用：

- 对象存储。
- 镜像内静态必需资源。
- PVC。
- 专用配置中心。

## 常见错误与排障

### Pod 启动时报 CreateContainerConfigError

```bash
kubectl describe pod <pod>
kubectl get configmap api-config -o yaml
kubectl get secret api-secret -o yaml
```

常见原因：

- ConfigMap 不存在。
- Secret 不存在。
- key 名写错。
- Secret 在另一个 namespace。
- `optional: false` 且引用对象缺失。

### 配置修改后服务没变化

```bash
kubectl get configmap api-config -o yaml
kubectl describe pod <pod>
kubectl rollout restart deploy/api
kubectl rollout status deploy/api
```

判断：

- 如果是 env 注入，需要重启 Pod。
- 如果是 volume 挂载，检查应用是否重新读取文件。
- 如果用了 `subPath`，不要期待自动刷新。
- 如果使用 Helm/Kustomize，确认新配置是否真的 apply。

### Debug Pod 没法访问目标服务

```bash
kubectl run netshoot -n prod --rm -it --image=nicolaka/netshoot -- bash
```

检查：

```bash
dig order.prod.svc.cluster.local
curl -v http://order:8080/ready
nc -vz order 8080
```

如果仍失败：

```bash
kubectl get svc order -n prod
kubectl get endpointslice -n prod -l kubernetes.io/service-name=order
kubectl get networkpolicy -n prod
kubectl get pod -n prod -l app=order -o wide
```

## 后端开发者检查清单

- [ ] 镜像不包含环境专属配置和密钥。
- [ ] 普通配置进入 ConfigMap，敏感配置进入 Secret。
- [ ] Secret 不被误认为加密，集群启用 etcd encryption at rest。
- [ ] Secret 访问权限按 namespace 和 ServiceAccount 最小化。
- [ ] 生产密钥不以明文 YAML 进入 Git。
- [ ] 必要时使用 External Secrets / Vault / 云厂商 Secret Manager。
- [ ] env / envFrom / volume / subPath 的更新语义已明确。
- [ ] 配置变更需要 rollout 时，有自动触发机制。
- [ ] 核心服务避免无控制地使用 envFrom。
- [ ] 应用启动时校验必需配置。
- [ ] 不在日志中打印完整环境变量。
- [ ] Secret 有轮换计划和审计机制。
- [ ] ConfigMap / Secret 命名和拆分符合服务边界。
- [ ] 对不可变生产配置考虑 `immutable: true`。
