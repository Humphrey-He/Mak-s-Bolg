# ZSet 为什么能同时支持点查和范围查

## 1. 本章要解决的问题

ZSet 能做排行榜、延迟队列、权重排序和时间线。它为什么既能按 member 快速查 score，又能按 score 做范围查询？答案在 dict + skiplist 的双结构设计。

## 2. 核心观点

ZSet 为了同时满足点查和有序范围查询，使用 dict 保存 member 到 score 的映射，使用 skiplist 维护 score 有序序列。小 ZSet 可用 listpack 节省内存，大 ZSet 才使用跳表。

## 3. 原理拆解

```mermaid
flowchart LR
    A[ZSet] --> B{小规模?}
    B -->|是| C[listpack]
    B -->|否| D[dict + skiplist]
    D --> E[dict: member -> score]
    D --> F[skiplist: score/member ordered]
    E --> G[ZSCORE O(1)]
    F --> H[ZRANGE/ZRANGEBYSCORE O(logN + M)]
```

跳表由多层前进指针组成，用概率方式构建索引层。它没有平衡树旋转那么复杂，实现简单，范围遍历自然。Redis 在 score 相同时用 member 字典序保证排序稳定。

## 4. 命令与代码示例

排行榜：

```bash
ZADD rank:game 100 user:1 80 user:2 120 user:3
ZREVRANGE rank:game 0 9 WITHSCORES
ZRANK rank:game user:1
ZSCORE rank:game user:3
ZINCRBY rank:game 10 user:1
```

延迟队列取到期任务：

```bash
ZADD delay:jobs 1730000000000 job:1
ZRANGEBYSCORE delay:jobs -inf 1730000000000 LIMIT 0 10
ZREM delay:jobs job:1
```

Lua 原子取任务：

```lua
local jobs = redis.call("ZRANGEBYSCORE", KEYS[1], "-inf", ARGV[1], "LIMIT", 0, ARGV[2])
for _, job in ipairs(jobs) do
  redis.call("ZREM", KEYS[1], job)
end
return jobs
```

## 5. 生产实践

ZSet 建模场景：

- 排行榜：score 是分数或热度。
- 延迟队列：score 是执行时间戳。
- 时间线：score 是事件时间。
- 权重调度：score 是优先级或下次调度时间。

生产 checklist：

- 排行榜定期裁剪，例如只保留前 N 或最近周期。
- 延迟队列取任务必须原子删除，避免重复消费。
- score 使用整数时间戳时注意毫秒和秒的统一。
- 大 ZSet 做范围删除要分批，例如 `ZREMRANGEBYRANK` 控制批量。

## 6. 常见坑

- 不裁剪排行榜，ZSet 无限增长。
- 延迟队列先查后删不是原子操作，多消费者重复取。
- score 使用浮点数后遇到精度问题。
- `ZRANGE 0 -1` 拉全量排行榜。

## 8. 章节笔记

- ZSet 的点查靠 dict，范围查靠 skiplist。
- 小 ZSet 可用 listpack 节省内存。
- score 设计决定业务语义，要注意精度和排序稳定性。
- 排行榜和延迟队列都要控制增长和原子性。

## 9. 小结

ZSet 是 Redis 中最有设计感的数据类型之一。它用双结构换取了丰富查询能力，也要求我们在生产中管理好规模、裁剪和并发消费。
