如果说大语言模型提供了推理与生成能力，那么工具调用就是 Agent 走向真实世界的接口。

没有工具调用，Agent 只能停留在"会说"的层面；有了工具调用，Agent 才能搜索资料、查询数据库、执行代码、操作文件、调用业务 API、转交任务，甚至参与完整工作流。

但工具调用不是简单地给模型几个函数名。一个可用于生产的工具调用系统，至少要回答五个问题：

```
1. 模型如何知道什么时候该调用工具？
2. 模型如何选择正确工具？
3. 模型如何生成正确参数？
4. 工具返回结果如何进入下一步推理？
5. 工具调用如何被权限、观测、评测和多 Agent 编排约束？
```

---

## 一、为什么工具调用是 Agent 的分水岭？

普通 LLM 应用通常是：

```
用户输入 → 模型生成文本 → 返回结果
```

Agent 应用则更像：

```
用户目标 → 模型判断下一步 → 调用工具 → 获取观察结果 → 更新状态 → 再次推理 → 继续调用工具或输出结果
```

区别不只是"有没有 function calling"，而是**模型输出是否能驱动外部动作**。

例如，用户问"帮我分析这个 GitHub 仓库最近的构建失败原因，并提出修复建议"。一个普通聊天模型只能根据用户粘贴的日志回答；一个 Agent 则可能会调用 GitHub API 获取最近 workflow runs、读取失败日志、检索相关代码文件、总结失败原因、生成 patch 建议、必要时创建 issue 或 PR。

## 二、Toolformer：模型能否自己学会使用工具？

Toolformer 研究的问题是：模型能否在少量示例下，自行学习何时调用工具、调用什么工具、传什么参数，以及如何把工具结果纳入后续生成。论文提出，语言模型虽然在少样本学习和指令跟随上能力很强，但在算术、事实查找等基础功能上仍会输给简单工具；Toolformer 试图让模型通过简单 API 获得这些外部能力。

Toolformer 的核心思想可以概括为：

```
不是人工标注大量工具调用数据，
而是让模型在原始文本中自监督地产生工具调用训练样本。
```

它的流程大致是：

```
1. 给每个 API 少量人工示例；
2. 让模型在普通文本中尝试插入 API 调用；
3. 执行这些 API 调用并得到结果；
4. 判断 API 结果是否能提升后续 token 预测概率；
5. 只保留真正有帮助的调用样本；
6. 用这些样本微调模型。
```

Toolformer 训练模型学会的不只是"调用某个 API"，而是四个决策：

```
When：什么时候调用？
Which：调用哪个工具？
How：传什么参数？
Use：如何使用工具结果？
```

Toolformer 的意义在于它证明了一件事：

> 工具调用可以被看成语言建模能力的一部分，而不是外部硬编码流程。

但 Toolformer 更偏训练范式，工具集合相对有限；生产环境中的 API 数量更大、文档变化更快、权限约束更复杂。这正是 Gorilla 进一步讨论的问题。

## 三、Gorilla：大规模 API 场景下，工具调用最大的敌人是 hallucination

Gorilla 聚焦的是另一个现实问题：当工具数量很多、API 功能重叠、文档持续变化时，模型如何准确生成 API 调用？论文指出，即使是强模型，在 API 调用上仍面临两个核心困难：**输入参数生成不准确**和**API hallucination**。

所谓 API hallucination，指的是模型生成了不存在的 API、错误的函数名、错误参数，或者把多个 API 的用法混在一起。

Gorilla 的方案包括两部分：

```
1. 使用 self-instruct fine-tuning 提升 API 调用生成能力；
2. 结合文档检索器，让模型在调用 API 前获得最新 API 文档。
```

它提出了 APIBench，覆盖 HuggingFace、TorchHub、TensorHub 等机器学习 API，并使用抽象语法树子树匹配来评估 API 调用的功能正确性。APIBench 包含约 1600 个 API，Gorilla 在准确率和降低 hallucination 上都有改进。

### 对生产系统的启发

Gorilla 对生产系统的启发非常直接：

> 工具调用的可靠性，不能只靠模型记忆；必须结合实时文档检索。

这意味着一个成熟工具调用系统应该有：

```
Tool Registry：保存工具元数据；
Tool Retriever：按任务检索候选工具；
Tool Documentation Store：保存工具说明、参数、示例；
Tool Invocation Validator：校验调用是否符合 schema；
Tool Execution Runtime：真正执行工具；
Tool Result Interpreter：把执行结果交还给模型。
```

也就是说，工具调用不是把所有工具塞进 prompt，而是：

```
先检索相关工具
→ 注入少量高相关工具
→ 让模型选择和调用
→ 校验参数
→ 执行
→ 返回结构化观察结果
```

工具数量越大，越不能把所有工具暴露给模型，否则会带来三类问题：**上下文污染**（工具描述太多，模型注意力分散）、**选择困难**（功能相似工具导致误选）、**安全风险**（模型看到不该用的高风险工具）。

## 四、LLM With Tools：工具增强 LLM 的标准范式

《LLM With Tools: A Survey》系统梳理了 LLM 使用外部工具的方法、挑战和发展。论文将问题抽象为从用户指令到可执行计划再到执行结果的流程。

从工程角度，可以把 LLM With Tools 的标准链路抽象为：

```
User Instruction
→ Intent Understanding
→ Tool Selection
→ Plan Generation
→ Tool Invocation
→ Observation Integration
→ Dynamic Plan Adjustment
→ Final Response
```

Survey 中提到的关键挑战，在工程中可以归纳为六类：

**调用时机**。模型需要知道什么时候应该自己回答，什么时候应该调用工具。过度调用会增加成本和延迟；调用不足会导致幻觉。

**工具选择**。当工具很多时，模型必须从候选集合中选择最合适的工具。

**参数生成**。工具名选对了，参数错了也会失败。

**结果解释**。工具返回的是结构化数据、错误码、日志还是自然语言？模型能否正确理解？

**计划修正**。工具失败时，模型是否能换工具、改参数、重试，还是直接编造答案？

**安全边界**。工具可能会读写文件、调用生产 API、发送消息或修改数据，必须有权限控制和人工确认。

## 五、什么是 Agent 友好的工具？

Anthropic 的工程文章《Writing effective tools for AI agents》指出，Agent 的效果很大程度取决于我们给它设计的工具质量；文章特别讨论了在 MCP 可以让 Agent 拥有大量工具的情况下，如何让这些工具真正有效。

这和传统 API 设计有本质区别。传统 API 面向的是程序员；Agent 工具面向的是模型。模型可能误解工具用途、忽略参数约束、重复调用、调用顺序错误，或者在错误结果上继续推理。

### 1. 工具名称要表达意图，不只表达资源

传统 API 可能叫 `get()`、`list()`、`update()`、`query()`，对模型来说太模糊。Agent 工具应该叫：

```
search_papers
get_article_by_slug
publish_article_to_github
validate_mdx_frontmatter
summarize_build_failure
```

工具名最好同时表达动作和对象。

### 2. 工具描述要说明何时使用

坏描述：`Search documents.`

好描述：`Search the internal document index for relevant articles, papers, or technical notes. Use this when the user asks about information that may exist in the knowledge base and current context is insufficient.`

模型需要的不只是"这个工具能做什么"，还需要"什么时候该用"。

### 3. 参数 schema 要尽量收窄

参数越结构化，模型越不容易乱填。

```json
{
  "query": "string",
  "top_k": "integer",
  "source_type": "paper | blog | docs",
  "date_range": "optional"
}
```

### 4. 工具返回值要结构化

结构化结果更容易被模型继续使用，也更容易被系统记录和评测。

```json
{
  "results": [
    {
      "title": "Toolformer",
      "url": "...",
      "abstract": "...",
      "score": 0.91
    }
  ]
}
```

### 5. 工具应该封装工作流，而不是暴露太细粒度 API

假设要发布文章。不要让模型直接接触 `git_add`、`git_commit`、`git_push`、`cloudflare_trigger_deploy`，更适合暴露：

```
publish_article(article_id)
```

内部再由系统执行生成 MDX → 校验 → Git commit → Git push → 记录发布任务。

> **面向 Agent 的工具应该按任务意图封装，而不是按底层技术步骤暴露。**

## 六、工具调用系统的分层设计

```
Tool Use System
├── Tool Registry
├── Tool Retriever
├── Tool Schema & Documentation
├── Tool Permission Layer
├── Tool Execution Runtime
└── Tool Observation & Evaluation
```

### 1. Tool Registry

工具注册中心保存所有工具元数据：

```ts
interface ToolDefinition {
  name: string;
  description: string;
  inputSchema: JSONSchema;
  outputSchema?: JSONSchema;
  category: "search" | "write" | "compute" | "deploy" | "handoff";
  riskLevel: "low" | "medium" | "high";
  requiresApproval: boolean;
}
```

### 2. Tool Retriever

当工具数量超过十几个，就不应该全部塞进模型上下文。需要先根据任务检索候选工具。这正是 Gorilla 带来的启发：面对庞大且变化的 API 集合，检索可以减少 hallucination，并让模型适应文档变化。

### 3. Tool Schema & Documentation

Schema 是工具调用可靠性的第一道防线。每个工具必须有 schema 和示例。

### 4. Tool Permission Layer

权限层决定当前用户、当前 Agent、当前任务能不能调用某个工具。这一步不能交给模型判断，必须由系统执行。

### 5. Tool Execution Runtime

执行层负责参数校验、权限校验、超时控制、失败重试、错误包装、审计日志、结果标准化。

### 6. Tool Observation & Evaluation

每次工具调用都应该被记录：tool_name、arguments、result、latency、error、caller_agent、trace_id、user_id、approved_by。

## 七、Handoff：多 Agent 协作为什么也是工具调用？

OpenAI Agents SDK 的 Handoffs 文档说明，handoff 允许一个 Agent 把对话或任务的一部分委托给另一个 Agent，适用于不同 Agent 专精不同领域的场景。Handoffs 会被表示为给 LLM 的工具：如果转交给 `Refund Agent`，工具名可能是 `transfer_to_refund_agent`。

这意味着多 Agent 协作不一定需要设计成复杂的"Agent 网络"，可以先建模为特殊工具调用：

```
transfer_to_research_agent
transfer_to_writer_agent
transfer_to_reviewer_agent
transfer_to_citation_checker
```

OpenAI 的 orchestration 文档区分了两类多 Agent 模式：一种是把 specialist agent 当作工具调用，主 Agent 保留最终答复责任；另一种是 handoff，让某个 specialist 接管对话或任务。

### Handoff 的两种模式

**Agent-as-Tool**：主 Agent 保持控制权。Manager Agent 调用 `Summarizer`、`Search Agent` 作为工具，但最终答案由 Manager 负责。适合主 Agent 需要统一最终输出、专家 Agent 只是辅助的场景。

**Handoff**：专家 Agent 接管控制权。Triage Agent 调用 `transfer_to_billing_agent`，Billing Agent 继续完整对话。适合任务类型明确切换、不同 Agent 有不同系统提示和工具权限的场景。

## 八、工具调用的安全边界

可以按风险把工具分为三类：

**只读工具**：`search_docs`、`get_article`、`list_files`，风险较低，可允许自动调用。

**写入工具**：`create_article`、`update_article`、`send_email`，需要权限控制，必要时人工确认。

**高风险工具**：`delete_file`、`deploy_production`、`run_shell_command`、`charge_payment`，默认不应该自动调用，必须人工确认、沙箱执行、参数白名单、审计日志、回滚方案。

> 模型可以建议高风险动作，但不应该默认直接执行高风险动作。

## 九、工具调用的评测指标

```
Tool Selection Accuracy：工具选择是否正确
Argument Accuracy：参数是否正确
Call Necessity：是否真的需要调用工具
Call Efficiency：是否调用过多工具
Execution Success Rate：工具执行成功率
Recovery Rate：工具失败后是否能恢复
Permission Violation Rate：是否尝试越权调用
Final Task Success：最终任务是否完成
```

对 API 调用类任务，可以借鉴 Gorilla 的思路，使用 AST 子树匹配来评估 API 调用的功能正确性。对业务工具，可以设计测试集验证工具调用路径是否符合预期。

## 十、常见反模式

### 把所有工具一次性暴露给模型

问题：上下文过长、工具选择混乱、高风险工具暴露。改进：先检索候选工具，只注入相关工具。

### 工具描述过短

坏例子：`publish article`

好例子：`Publish a validated draft article to the GitHub content repository. This tool generates MDX, commits it to the configured branch, and triggers the static site deployment. Use only after validation passes.`

### 工具粒度太细

不要让模型处理 `git add`、`git commit`、`git push`，应封装为 `publish_article`。

### 没有失败语义

工具失败不能只返回 `failed`，应返回结构化错误码和是否可重试。

### 没有人工确认

发布、删除、部署、付款、发邮件这类工具都应该有人工确认。

## 十一、以博客 CMS Agent 为例

结合博客 CMS，可以设计一组 Agent 工具。

**只读工具**：`list_articles`、`get_article_by_slug`、`search_posts`、`list_tags`、`get_publish_status`

**写入工具**：`create_draft_article`、`update_draft_article`、`validate_article`、`generate_mdx`、`publish_article`

**高风险工具**：`delete_article`、`force_push_content_repo`、`rollback_to_commit`、`deploy_production`

**Handoff 工具**：`transfer_to_research_agent`、`transfer_to_writer_agent`、`transfer_to_reviewer_agent`、`transfer_to_seo_agent`

一个写作 Agent 的流程：

```
用户：帮我写一篇关于 Toolformer 和 Gorilla 的技术文章。

Research Agent：
  search_papers
  summarize_paper

Writer Agent：
  create_draft_article
  update_draft_article

Reviewer Agent：
  validate_article
  check_citations

CMS Agent：
  publish_article
```

## 十二、结论：工具调用是 Agent 的动作系统

Toolformer 证明了模型可以学习何时、如何调用工具；Gorilla 证明了在大规模 API 环境中，检索和微调可以显著降低 API hallucination；LLM With Tools 的综述提醒我们，工具增强 LLM 是一个包含意图理解、工具选择、计划生成、执行和动态调整的完整范式；Anthropic 的工程文章强调 Agent 的效果高度依赖工具设计质量；OpenAI Agents SDK 的 Handoff 则说明，多 Agent 协作本身也可以被建模为一种工具调用。

因此，Agent 工具调用系统的核心不是"给模型几个函数"，而是构建一套完整的动作系统：

```
工具注册 / 工具检索 / 工具描述 / 参数 schema
权限控制 / 执行运行时 / 人工确认 / 调用日志
失败恢复 / 调用评测 / 多 Agent handoff
```

如果模型是 Agent 的大脑，工具就是 Agent 的手。但真正决定 Agent 是否可靠的，不是手有多多，而是每只手是否被正确命名、正确授权、正确观测、正确评测。
