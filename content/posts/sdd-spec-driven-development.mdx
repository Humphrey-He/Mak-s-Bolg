在 AI 编码助手普及之后，软件开发的效率被大幅拉高，但另一个问题也被放大了：**需求越模糊，AI 生成的代码越容易偏离真实意图**。

很多团队已经体验过类似场景：一句"帮我实现登录功能"，AI 很快生成了代码，但认证方式、异常处理、字段校验、权限边界、接口契约都可能与团队预期不一致。表面上看，代码写得更快了；实际上，调试、返工和沟通成本被转移到了后面。

这正是 **Spec-Driven Development（SDD，规范驱动开发）** 试图解决的问题。

SDD 的核心思想很直接：**先把系统应该做什么定义清楚，再让人或 AI 去实现它**。规范不再是项目结束后补写的文档，而是开发过程中的核心工件，是产品、研发、测试、AI 编码助手共同遵循的事实来源。

## 一、什么是 SDD？

**SDD（Spec-Driven Development，规范驱动开发）** 是一种以规范为中心的软件开发范式。它强调在编码之前，先用结构化、可验证、可协作的方式定义系统行为，再基于规范进行技术设计、代码实现和验证。

与传统"代码先行、文档后补"的方式不同，SDD 会把规范前置，并要求代码始终与规范保持一致。代码可以由规范生成，也可以由开发者或 AI 编码助手实现，但最终都需要通过规范来验证。

可以简单理解为：

> 传统开发是"先写代码，再解释代码"；SDD 是"先定义行为，再生成或实现代码"。

在 AI 辅助开发场景下，SDD 的价值尤其明显。规范可以成为 AI 的"超级提示词"，让 AI 不再基于模糊描述自由发挥，而是基于清晰的接口、行为、边界和验收标准生成代码。

## 二、为什么 SDD 重新变得重要？

SDD 并不是一个全新的概念。TDD、BDD、契约测试、模型驱动开发中都能看到类似思想：先定义预期，再实现代码。

但在 AI 编码时代，SDD 的重要性被重新放大，主要有三个原因。

### 1. AI 放大了需求歧义

AI 很擅长生成代码，但它无法天然理解团队的业务语境、架构约束和边界条件。如果输入只是几句自然语言需求，AI 往往会根据通用经验补全细节。

这会带来一个典型问题：**AI 生成的代码看起来合理，但并不一定符合真实业务规则**。

例如，同样是"创建订单接口"，不同团队可能对库存校验、优惠券锁定、支付超时、幂等控制、异常码设计有完全不同的约定。如果没有规范，AI 只能猜。

### 2. 多人协作需要统一事实来源

在企业级系统中，产品、研发、测试、前端、后端、运维、业务方经常对同一功能有不同理解。需求文档、接口文档、测试用例、代码实现之间如果缺少同步机制，很容易出现"每个人都以为自己理解对了"的情况。

SDD 的作用，是把规范变成共同基准：

- 产品用规范表达业务意图；
- 开发用规范约束实现边界；
- 测试用规范设计验证用例；
- AI 用规范生成更准确的代码；
- 运维和后续维护者用规范理解系统行为。

### 3. 长期维护需要可追溯性

一个系统真正的成本，往往不在第一次开发，而在持续迭代和长期维护。

当代码和文档脱节时，新人只能通过阅读代码猜测业务意图；当测试和需求脱节时，自动化测试只能证明"代码符合测试"，却不能证明"代码符合业务"。

SDD 通过规范建立从需求到代码、从代码到验证的追溯链路，让系统行为更容易被解释、验证和演进。

## 三、SDD 的三种落地层级

SDD 不是一种固定流程，而是一组可以按项目复杂度逐步加强的工程实践。实际落地时，通常可以分为三个层级：**Spec-First、Spec-Anchored、Spec-as-Source**。

### 1. Spec-First：规范先行

**Spec-First** 是 SDD 的入门模式。它要求在开发前先写规范，用规范明确目标和边界，但不强制规范在后续迭代中持续与代码同步。

它的核心价值是：**在开发开始前消除主要歧义**。

这种模式适合原型、小工具、一次性功能，或者团队刚开始引入 SDD 的阶段。规范可以是 Markdown 文档、接口草稿、流程说明，也可以是简单的验收标准清单。

关键要求不是"写得多完整"，而是"足够清楚，能指导实现"。

适用场景包括：

- AI 辅助开发新功能，希望减少 AI 自由发挥；
- 原型验证或一次性工具；
- 团队首次尝试 SDD；
- 需求仍在探索，但核心方向需要对齐。

Spec-First 的风险是规范容易在代码完成后失去维护价值。因此它更适合作为轻量实践，而不是长期系统的主流程。

### 2. Spec-Anchored：规范锚定

**Spec-Anchored** 是生产级系统中最常见、也最务实的 SDD 模式。

在这种模式下，规范不只是开发前的说明文档，而是随代码一起维护的"活文档"。任何功能变更、接口调整、错误处理变化，都需要先更新规范，再修改代码，并通过自动化测试或契约测试保证二者一致。

它的核心价值是：**让规范和代码互相锚定，避免规范漂移**。

常见做法包括：

- 使用 OpenAPI 定义 REST API 契约；
- 使用 Protobuf 定义 gRPC 服务契约；
- 使用 Gherkin 描述 BDD 场景；
- 使用 Pact、Specmatic、Cucumber 等工具做自动化校验；
- 将规范校验纳入 CI/CD 流水线。

适用场景包括：

- 企业级生产系统；
- 跨团队协作的微服务体系；
- 长期维护的核心业务模块；
- 需要降低需求理解偏差和集成成本的项目。

Spec-Anchored 是多数团队最值得优先落地的形态，因为它在规范严谨性和工程效率之间取得了较好的平衡。

### 3. Spec-as-Source：规范即源码

**Spec-as-Source** 是 SDD 的最高强度模式。

在这种模式下，规范是唯一由人类直接维护的核心工件，代码则由规范自动生成。开发者不直接修改生成代码，而是通过修改规范来驱动系统变化。

它的核心价值是：**从机制上消除规范与代码不一致的问题**。

这类模式常见于标准化程度高、代码生成工具成熟、合规要求严格的领域，例如：

- 汽车嵌入式控制软件；
- 航空航天与工业控制系统；
- 基于模型的控制算法开发；
- 标准化 API 客户端或 SDK 生成；
- 低代码平台和配置驱动系统。

Spec-as-Source 对规范质量和工具链要求极高。规范必须足够完整、精确、可生成，工具也必须足够可靠。因此它不适合所有团队，也不应该被当作 SDD 的默认目标。

对大多数业务系统而言，从 Spec-First 起步，逐步进入 Spec-Anchored，通常比直接追求 Spec-as-Source 更现实。

## 四、SDD 的标准工作流

无论采用哪一种层级，SDD 通常都可以拆解为四个阶段：**Specify → Plan → Implement → Validate**。

### 阶段一：Specify，定义规范

这个阶段的目标是回答：**系统应该做什么？**

规范需要描述系统的输入、输出、行为、边界条件和验收标准，但不应该过早绑定具体实现方案。

例如，不要只写"接口要快"，而要写：

> 查询订单接口在 99% 请求下响应时间不超过 200ms。

不要只写"参数不能为空"，而要明确：

> 当 userId 缺失时，接口返回 400，错误码为 USER_ID_REQUIRED。

好的规范应该具备几个特征：

- 能被产品、开发和测试共同理解；
- 能转化为测试用例；
- 能作为 AI 编码助手的输入；
- 能明确核心路径、异常路径和边界条件；
- 尽量描述"做什么"，避免描述"怎么做"。

### 阶段二：Plan，技术规划

这个阶段的目标是回答：**如何在规范边界内实现系统？**

如果说 Specify 关注业务行为，那么 Plan 关注工程实现。这个阶段会确定技术栈、架构设计、数据模型、接口划分、安全策略、性能方案和任务拆解。

在 AI 辅助开发中，这一步尤其重要。因为 AI 不只需要知道功能做什么，还需要知道团队希望它如何落地。例如：

- 使用 Spring Boot 3.x；
- 数据库采用 PostgreSQL；
- 接口认证使用 JWT；
- 错误响应遵循统一错误码结构；
- 单元测试使用 JUnit 5；
- 所有接口必须满足 OpenAPI 契约。

技术规划可以减少 AI 生成"能运行但不符合团队规范"的代码。

### 阶段三：Implement，落地实现

这个阶段的目标是：**基于规范和技术规划实现代码**。

实现可以由开发者完成，也可以由 AI 编码助手生成初稿，再由开发者审查、调整和补足边界条件。

更稳妥的方式是小步迭代：

1. 按规范拆分功能模块；
2. 每次只实现一个明确行为；
3. 实现后立即运行对应测试；
4. 如果发现规范遗漏，先回到 Specify 更新规范；
5. 再继续实现代码。

这里最忌讳的是：开发过程中发现规范不完整，于是开发者或 AI 擅自补逻辑。这样会让规范失去权威性，也会重新把团队带回"代码先行"的状态。

### 阶段四：Validate，验证闭环

这个阶段的目标是：**证明代码确实符合规范**。

验证不应只依赖人工测试，而应该尽可能自动化。例如：

- OpenAPI 契约测试；
- BDD 场景自动化执行；
- 单元测试；
- 集成测试；
- 性能阈值校验；
- 安全规则扫描。

如果代码与规范不一致，通常应优先修正代码；如果规范本身不合理，则需要先评审并更新规范，再基于新规范修改代码。

这一步的关键不是"测试通过"这么简单，而是建立一个闭环：

> 规范定义预期，代码实现预期，验证证明代码符合预期。

## 五、SDD 常用工具链

SDD 的落地不一定需要复杂工具链。更推荐的方式是从轻量工具开始，再根据团队成熟度逐步增强自动化能力。

### 1. 规范编写工具

用于把需求表达成结构化规范。

常见选择包括：

- API 场景：OpenAPI、Swagger Editor、GraphQL Schema；
- 微服务通信：Protobuf、AsyncAPI；
- 业务行为：Gherkin、Cucumber Studio；
- 通用文档：Markdown、GitBook、Confluence、Notion；
- 嵌入式与控制系统：Simulink、SCADE。

### 2. 契约测试与自动化校验工具

用于验证代码是否符合规范。

常见选择包括：

- API 契约测试：Pact、Specmatic；
- BDD 自动化：Cucumber、SpecFlow、Behave；
- 单元测试：JUnit、pytest、RSpec；
- CI 集成：GitHub Actions、GitLab CI、Jenkins。

### 3. AI 辅助开发工具

用于把规范转化为代码草稿、测试用例或重构建议。

常见选择包括：

- GitHub Copilot；
- Cursor；
- JetBrains AI；
- Amazon Kiro；
- GitHub Spec Kit；
- 其他支持上下文工程和规范输入的 AI 编码工具。

这类工具的关键不是"让 AI 自由写代码"，而是让 AI 在规范、架构约束和测试反馈中工作。

### 4. 代码生成工具

用于从规范直接生成代码框架、客户端 SDK 或完整实现。

常见选择包括：

- OpenAPI Generator；
- gRPC / Protobuf 代码生成；
- Simulink Coder；
- SCADE Suite；
- 低代码或配置驱动平台。

需要注意的是，代码生成越深入，对规范质量和工具可靠性的要求越高。团队不应为了"看起来先进"而过早引入重型生成工具。

## 六、典型应用场景

### 场景一：微服务 API 开发

在微服务架构中，服务之间的接口契约是协作基础。如果没有统一规范，不同团队很容易在字段含义、错误码、状态码、分页规则、认证方式上产生偏差。

采用 SDD 后，可以先用 OpenAPI 或 Protobuf 定义接口契约，再基于契约生成 Mock 服务、客户端代码、服务端接口骨架和契约测试。

这样前端、后端、测试可以并行工作，集成阶段的问题也会明显减少。

**推荐模式：Spec-Anchored**。

### 场景二：复杂业务系统开发

对于项目管理、审批流、订单、结算、风控等业务系统，真正复杂的往往不是代码，而是业务规则。

这类系统适合用 Gherkin 或结构化 Markdown 描述核心业务场景，例如：

```gherkin
Feature: 任务状态流转

Scenario: 普通成员完成任务
  Given 用户是任务负责人
  And 任务状态为"进行中"
  When 用户点击"完成任务"
  Then 任务状态变为"已完成"
  And 系统记录完成时间
```

这种写法让产品、开发和测试能围绕同一套场景讨论，减少"产品以为说清楚了，开发以为理解对了"的问题。

**推荐模式：Spec-Anchored**。

### 场景三：AI 辅助原型开发

在原型阶段，团队通常追求速度，不适合引入复杂流程。但这并不意味着可以完全没有规范。

比较实用的做法是：先写一份轻量 Markdown 规范，明确核心功能、核心接口、关键字段和验收标准，然后把它作为 AI 编码助手的主要上下文。

这样既不会让规范成本过高，又能显著减少 AI 生成代码时的偏差。

**推荐模式：Spec-First**。

### 场景四：安全关键或强合规系统

在汽车、航空、工业控制、金融核心链路等场景中，系统需要更高的可追溯性和确定性。

这类项目可能需要通过模型、状态机、形式化规范或强类型契约来定义系统行为，并通过工具生成代码或执行严格验证。

**推荐模式：Spec-as-Source 或强约束的 Spec-Anchored**。

## 七、SDD 与其他开发模式的区别

| 对比维度 | SDD | 传统代码先行 | Vibe Coding | TDD / BDD |
|------|------|------|------|------|
| 核心工件 | 规范 | 代码 | 模糊提示和直觉 | 测试或场景 |
| 开发顺序 | 先规范，再实现 | 先实现，再补文档 | 先让 AI 生成，再反复调试 | 先写测试，再写代码 |
| 歧义处理 | 通过规范前置消除 | 依赖沟通和经验 | 歧义最多 | 通过测试部分消除 |
| AI 适配性 | 高，规范可作为高质量上下文 | 中，依赖代码上下文 | 低，容易跑偏 | 中高，测试可作为约束 |
| 可追溯性 | 强 | 弱 | 很弱 | 中等 |
| 适用场景 | 企业级系统、微服务、合规系统、AI 辅助开发 | 小型项目或需求稳定项目 | 原型探索、小工具 | 注重质量的中小型项目 |

SDD 和 TDD / BDD 并不冲突。更准确地说，TDD / BDD 可以成为 SDD 的一部分。

SDD 关注的是更上层的规范体系：需求、接口、行为、约束和验证闭环；TDD / BDD 更偏向测试驱动实现。一个成熟团队完全可以用 SDD 定义整体规范，用 BDD 描述业务场景，用 TDD 保证代码质量。

## 八、落地 SDD 的常见风险

### 1. 过度规范

有些团队一开始就想把所有细节写进规范，甚至把伪代码、数据库表设计、框架细节都塞进规范里。结果规范变得庞大难维护，开发效率反而下降。

规避方式是坚持一个原则：**规范优先描述"做什么"，技术方案再描述"怎么做"**。

不同层级的规范颗粒度也应该不同：

- Spec-First：只覆盖核心行为和验收标准；
- Spec-Anchored：覆盖核心路径、关键边界和错误处理；
- Spec-as-Source：才需要接近完整系统定义。

### 2. 规范漂移

如果规范只在项目开始时写一次，后续代码迭代不再同步更新，它很快就会变成过期文档。

规避方式是把规范纳入版本控制，并在 CI/CD 中增加规范校验。对于 Spec-Anchored 模式，规范不更新、契约测试不通过，就不应允许合并或发布。

### 3. 工具链过重

SDD 不是工具堆砌。一次性引入 OpenAPI、契约测试、BDD、代码生成、模型工具和复杂流水线，很容易让团队产生抵触。

更合理的路径是：

1. 先用 Markdown 或 OpenAPI 做轻量规范；
2. 再引入基础自动化测试；
3. 然后接入契约测试和 CI；
4. 最后再考虑代码生成或模型驱动。

### 4. 规范变成流程负担

如果规范评审只追求形式完整，而没有真正消除歧义，SDD 就会变成官僚流程。

好的规范评审应该关注三个问题：

- 业务意图是否清楚？
- 开发是否能据此实现？
- 测试是否能据此验证？

只要这三个问题没有回答清楚，规范就还没有达到应有价值。

### 5. 对规范产生虚假信心

规范本身也可能是错的。如果团队只验证代码是否符合规范，却不验证规范是否符合真实业务，就可能把错误需求精确地实现出来。

因此，SDD 仍然需要业务评审、用户反馈和持续复盘。自动化验证只能证明"代码符合规范"，不能自动证明"规范一定正确"。

### 6. AI 与规范适配不佳

有些规范适合人看，但不适合 AI 解析。例如描述过于散文化、字段定义不完整、边界条件分散在多个段落中，都会影响 AI 生成质量。

面向 AI 的规范应该尽量结构化：

- 字段类型明确；
- 必填与可选明确；
- 错误码明确；
- 输入、操作、输出明确；
- 验收标准可测试；
- 技术约束集中说明。

这会显著提升 AI 生成代码和测试的稳定性。

## 九、如何开始落地 SDD？

如果团队还没有 SDD 基础，不建议一上来就建设完整工具链。更实用的落地路径可以分为四步。

### 第一步：从一个高痛点场景试点

优先选择最容易出现歧义和返工的场景，例如：

- 跨团队 API；
- 高频变更的业务流程；
- AI 生成代码经常跑偏的模块；
- 测试验收争议较多的功能。

不要从最复杂、最核心、风险最高的系统开始。

### 第二步：建立最小规范模板

先定义团队统一模板，例如：

- 背景与目标；
- 术语定义；
- 核心行为；
- 输入输出；
- 边界条件；
- 错误处理；
- 验收标准；
- 非功能约束。

模板不要太复杂，重点是让团队形成共同表达方式。

### 第三步：把规范接入开发流程

轻量阶段可以只要求 PR 中附带规范链接。成熟之后，可以把 OpenAPI 校验、契约测试、BDD 测试逐步接入 CI。

核心目标是让规范从"文档"变成"工程约束"。

### 第四步：让 AI 基于规范工作

当规范稳定后，可以把它作为 AI 编码助手的主要上下文，要求 AI 按规范生成代码、测试和接口实现。

一个实用提示词模板是：

```
请严格基于以下规范实现代码。
不要添加规范中没有定义的业务行为。
如果规范存在缺失或歧义，请先指出问题，不要自行假设。
实现需满足以下技术约束：
- 技术栈：...
- 数据库：...
- 测试框架：...
- 错误码规范：...
```

这个提示词的关键不是让 AI "更聪明"，而是限制 AI 不要随意补业务逻辑。

## 十、总结：SDD 的本质是让开发重新回到确定性

SDD 的价值，不在于多写几份文档，也不在于引入多少工具，而在于重新建立软件开发中的确定性。

它让团队先回答清楚：

- 系统到底要做什么？
- 哪些行为是明确要求？
- 哪些边界必须处理？
- 什么才算完成？
- 代码如何证明自己符合预期？

在传统开发中，这些问题常常分散在会议、口头沟通、需求文档、测试用例和代码注释里。SDD 则试图把它们收敛到一套可维护、可验证、可协作的规范中。

尤其在 AI 编码时代，SDD 不只是工程管理方法，更是一种 AI 协作方法。没有规范，AI 很容易成为"快速制造不确定性"的工具；有了规范，AI 才更可能成为稳定、可靠、高效的开发助手。

对多数团队来说，SDD 的最佳实践不是一步到位，而是渐进式落地：

> 从 Spec-First 开始消除歧义，用 Spec-Anchored 建立工程闭环，在少数高确定性领域探索 Spec-as-Source。

当规范成为团队共同认可的事实来源，代码、测试、文档和 AI 才能真正围绕同一个目标工作。
