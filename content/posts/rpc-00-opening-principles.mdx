# 00 开篇词：别老想着怎么用好 RPC 框架，你得多花时间琢磨原理

很多人第一次接触 RPC，是从 Dubbo、gRPC、Thrift、Spring Cloud OpenFeign 这些框架开始的。会写接口、会配注册中心、会调超时时间，似乎就算“会 RPC”了。但只要系统进入真实生产环境，问题就会变得不那么客气：一次调用为什么偶发超时？为什么下游挂了还在发请求？为什么改了一个字段就导致老客户端解析失败？为什么换了序列化协议后性能反而不稳定？

这些问题不是“多背几个配置项”能解决的。RPC 框架的核心价值，是把一次跨进程、跨机器、跨语言的远程调用，伪装成一次普通的本地方法调用；而它的工程难点，也恰恰藏在这个“伪装”背后。

## 本章要解决的问题

这一章不急着进入某个框架的 API，而是先回答三个更底层的问题：

- RPC 到底解决了什么问题？
- 为什么不能只停留在“会用框架”的层面？
- 学习 RPC 时，应该按怎样的知识地图展开？

如果你希望后面看协议、序列化、网络 IO、动态代理、服务发现、重试、熔断这些章节时不散，那么这篇就是整个系列的入口地图。

## 核心观点

RPC 不是一个单点技术，而是一组跨进程通信能力的组合。它至少包含调用抽象、协议设计、序列化、网络通信、服务发现、负载均衡、超时重试、流量治理、安全与可观测性。

学习 RPC 的关键，不是记住某个框架的默认配置，而是理解它为什么这样设计。框架会变化，Dubbo、gRPC、Thrift、brpc、CloudWeGo Kitex 的实现细节也各有取舍，但它们面对的问题高度相似：如何让远程调用更像本地调用，同时又不掩盖远程调用的成本和风险。

一句话概括：RPC 的目标是简化调用体验，但工程师必须理解被简化掉的复杂性。

## 原理拆解

一次最小的 RPC 调用，可以抽象成下面这条链路：

```mermaid
flowchart LR
    A[业务代码调用接口] --> B[客户端代理]
    B --> C[请求封装]
    C --> D[序列化]
    D --> E[协议编码]
    E --> F[网络传输]
    F --> G[服务端协议解码]
    G --> H[反序列化]
    H --> I[服务分发与反射调用]
    I --> J[业务实现]
    J --> K[响应返回]
    K --> L[客户端收到结果]
```

这条链路看起来直观，但每个节点都藏着取舍。

客户端代理负责让调用方像调用本地接口一样发起调用。它屏蔽了网络细节，却也容易制造“远程调用就是本地调用”的错觉。

协议负责描述消息边界、请求类型、序列化方式、状态码、版本号和扩展字段。协议设计得好，系统可以平滑升级；设计得差，一个字段变化就可能引发兼容性事故。

序列化负责把对象变成字节流。JSON 可读性好，Protobuf 体积小、跨语言强，Hessian 对 Java 生态友好，但每种方案都有性能、兼容性和安全边界。

网络通信负责把字节发出去并收回来。高并发 RPC 通常不会为每个请求创建一个线程和一个短连接，而是倾向长连接、连接池、异步 IO、事件循环和请求复用。

服务治理负责在故障、发布、扩容、降级时维持系统稳定。注册中心、健康检查、路由、负载均衡、重试、限流、熔断，并不是锦上添花，而是 RPC 真正能上生产的必要条件。

## 工程实践

真正掌握 RPC，建议按四层路线推进。

第一层，理解一次调用的生命周期。你要能画出从客户端代理到服务端执行再到响应返回的完整链路，并能说清楚每一步可能失败在哪里。

第二层，理解框架核心模块。至少包括 Proxy、Protocol、Codec、Transport、Registry、Cluster、Filter、Config 这些边界。以后读 Dubbo 或 gRPC 源码时，不要被类名淹没，要先找到模块职责。

第三层，理解生产治理。一个可演示的 RPC Demo 很容易写，一个能扛发布、扩容、故障和流量突刺的 RPC 系统很难。超时、重试、幂等、熔断、限流、优雅上下线、可观测性，要作为一组组合拳来看。

第四层，理解演进能力。线上系统很少从零开始，更多时候是协议迁移、序列化替换、框架升级、多语言接入、流量回放验证。RPC 的高级能力往往服务于“带着历史包袱继续演进”。

## 常见坑

最常见的坑，是把 RPC 当成本地调用。远程调用有网络延迟、失败概率、超时、重试、副作用和序列化成本。一个本地方法可以假设毫秒内完成，RPC 不行。

第二个坑，是只关注平均耗时。RPC 链路更应该关注 P95、P99、超时率、错误率、连接池水位、队列堆积和下游依赖状态。平均值很好看，不代表用户体验稳定。

第三个坑，是滥用重试。重试可以提高短暂故障下的成功率，也会放大下游压力。没有总超时预算、幂等保护和退避策略的重试，常常是故障放大器。

第四个坑，是忽视协议兼容。字段删除、类型变化、语义变化、枚举值新增，都可能导致老客户端或老服务端出现不可预期行为。协议一旦大规模上线，就要像数据库表结构一样谨慎演进。

## 面试追问

1. RPC 和 HTTP API 的区别是什么？

RPC 更强调“调用远程方法”的抽象，通常有接口定义、代理、序列化协议和服务治理能力；HTTP API 更强调资源或接口暴露，天然适合开放平台、浏览器生态和跨组织集成。二者并不对立，gRPC 本身就运行在 HTTP/2 之上。

2. 为什么说 RPC 不能完全等同于本地调用？

因为远程调用存在网络不确定性、对端故障、序列化成本、超时和重试语义。本地调用失败通常是进程内异常，RPC 失败可能是网络、服务端、注册中心、限流、协议兼容等多个环节造成的。

3. 为什么很多 RPC 框架都要做服务治理？

单纯通信只能解决“能不能调到”的问题，服务治理解决“调哪个、怎么调、失败怎么办、流量怎么控、发布怎么稳”的问题。没有治理能力，RPC 很难支撑大规模微服务系统。

4. 学 RPC 应该先看源码还是先看原理？

先看主流程原理，再带着问题看源码。源码不是小说，直接钻进去容易迷路。先明确调用链路、模块边界和扩展点，再阅读 Dubbo、gRPC、Netty 等项目，效率会高很多。

## 章节笔记

### 课程核心观点

RPC 的重点不是“怎么把框架用熟”，而是理解框架背后的通信、抽象和治理逻辑。框架 API 会变，但跨进程调用面临的问题不会变。

### 我的理解

RPC 是分布式系统里最容易被低估的基础设施。它表面上只是一次接口调用，实际连接着协议、网络、线程模型、注册发现、故障处理和工程演进。越是大规模系统，越不能只把它当工具库。

### 关键概念

- 本地调用语义：调用方像调本地接口一样使用远程服务。
- 远程调用成本：网络延迟、失败概率、序列化、连接管理。
- 服务治理：注册发现、路由、负载均衡、重试、熔断、限流。
- 可演进性：协议兼容、多版本共存、灰度发布、流量回放。

### 实战落地

为自己的系统补一张 RPC 全景图：调用方、服务方、注册中心、配置中心、网关、监控、日志、链路追踪、限流熔断组件都画出来。然后追踪一次真实调用，记录请求经过了哪些模块、有哪些超时配置、哪些指标能观察到它。

### 生产坑点

- 只设置客户端超时，不设置服务端任务取消。
- 只看成功率，不看慢调用和重试次数。
- 接口字段随意修改，没有兼容策略。
- 发布时没有优雅关闭和启动预热。

## 小结

RPC 的学习应该从“调用发生了什么”开始，再扩展到“框架如何组织这些能力”，最后落到“生产环境如何稳定运行”。后面的章节会按这个路径展开：先拆通信流程，再看协议、序列化、网络 IO 和动态代理，最后逐步进入框架设计与服务治理。
