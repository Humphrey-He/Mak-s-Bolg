# Redis 实战建模进阶：从对象缓存、排行榜、消息流到大 key/热 key 治理

## 前言

Redis 不只是缓存，也不是简单的 `GET` / `SET` 工具。真正把 Redis 用好，核心在于两件事：

```text
1. 能不能把业务访问模式映射到合适的数据结构；
2. 能不能在数据规模变大、流量变高之后控制住风险。
```

很多 Redis 问题不是出在命令不会用，而是出在建模阶段。

比如：

```text
用户对象到底用 String JSON 还是 Hash？
排行榜为什么用 ZSet？
延迟队列能不能用 ZSet 做？
Redis Stream 能不能替代 Kafka？
Bitmap 适合什么统计？
HyperLogLog 什么时候不能用？
大 key 和热 key 为什么会拖垮 Redis？
```

这些问题本质上都不是单个命令问题，而是数据建模、访问模式、内存成本、延迟风险和架构边界的问题。

本文站在开发和架构角度，深挖几个 Redis 高价值实战专题：

```text
1. String JSON vs Hash：对象缓存建模
2. ZSet：排行榜和延迟队列
3. Stream：消费者组机制
4. Bitmap：签到和活跃统计
5. HyperLogLog：UV 估算
6. 大 key / 热 key 治理规范
```

目标不是背命令，而是建立一套生产环境可用的 Redis 选型方法。

---

# 一、String JSON vs Hash：对象缓存怎么建模？

对象缓存是 Redis 最常见的使用场景之一。

比如用户信息、商品详情、订单摘要、文章详情、权限快照，都可以放进 Redis。

但一个经典问题是：

```text
对象应该用 String 存 JSON，还是用 Hash 存字段？
```

这个问题没有绝对答案，关键看访问模式。

---

## 1. String JSON 模型

String JSON 是最直观的对象缓存方式。

例如商品详情：

```text
SET product:detail:1001 '{"id":1001,"name":"iPhone","price":6999,"stock":100}' EX 300
GET product:detail:1001
```

应用侧拿到 JSON 后反序列化成对象。

### 适合场景

String JSON 适合整对象读写。

典型场景：

```text
商品详情页缓存
文章详情缓存
用户权限快照
首页聚合接口缓存
复杂对象的查询结果缓存
```

这些场景有一个共同点：

```text
读的时候通常需要整个对象。
```

例如商品详情页请求进来后，前端通常需要商品名称、价格、图片、库存、描述、标签等完整信息。此时 Redis 存一份 JSON，读取后直接返回或反序列化，模型很简单。

### 优点

```text
1. 模型简单
2. 和业务 DTO / VO 对象天然对应
3. 一次 GET 就能拿到完整对象
4. 适合接口级缓存
5. 方便整体序列化和压缩
```

String JSON 对开发非常友好。业务代码通常只需要：

```text
查 Redis
反序列化 JSON
返回对象
```

对于聚合接口缓存尤其方便。

比如一个商品详情接口可能聚合了：

```text
商品基础信息
库存信息
价格信息
营销标签
店铺信息
推荐信息
```

如果这些信息每次都要分别查数据库和 RPC，成本很高。可以把聚合结果整体序列化成 JSON 放进 Redis。

---

## 2. String JSON 的问题

String JSON 的最大问题是局部更新成本高。

例如用户对象：

```json
{
  "id": 1001,
  "name": "Tom",
  "age": 20,
  "city": "Tokyo",
  "avatar": "xxx",
  "level": 5
}
```

如果只想更新 `avatar`，String JSON 模型通常要：

```text
1. GET 整个 JSON
2. 反序列化
3. 修改 avatar 字段
4. 重新序列化
5. SET 整个 JSON
```

这会带来几个问题：

```text
1. 网络传输的是整个对象
2. 应用侧有序列化/反序列化成本
3. 并发更新不同字段时可能互相覆盖
4. 大对象更新成本高
```

例如两个线程同时更新：

```text
线程 A 更新 avatar
线程 B 更新 city
```

如果都是先 GET 后 SET 整个 JSON，就可能出现后写覆盖先写的问题。

当然可以用分布式锁、版本号、Lua 脚本、数据库最终覆盖等方式处理，但复杂度会上升。

---

## 3. Hash 模型

Hash 是 Redis 内部的 field-value 结构。

例如用户资料：

```text
HSET user:profile:1001 id 1001 name Tom age 20 city Tokyo avatar xxx level 5
HGET user:profile:1001 name
HSET user:profile:1001 avatar new_avatar
HGETALL user:profile:1001
```

Hash 的核心优势是字段级读写。

### 适合场景

```text
用户基础资料
设备状态
用户在线状态
购物车字段
风控状态
会话属性
轻量配置对象
```

这些场景有一个共同点：

```text
经常只读写对象中的部分字段。
```

例如用户在线状态：

```text
HSET user:status:1001 online 1 lastActiveTime 1717392000 device mobile
HGET user:status:1001 online
```

如果只需要判断用户是否在线，没必要读取整个用户对象。

---

## 4. Hash 的优势

Hash 相比 String JSON，主要优势有：

```text
1. 支持字段级更新
2. 支持字段级读取
3. 避免整对象反序列化
4. 小对象在 Redis 内部可能更省内存
5. 适合对象状态频繁变化的场景
```

例如购物车：

```text
HSET cart:user:1001 sku:2001 2
HSET cart:user:1001 sku:2002 1
HINCRBY cart:user:1001 sku:2001 1
```

这比把整个购物车 JSON 取出来、修改、再写回更自然。

---

## 5. Hash 的问题

Hash 不是万能对象模型。

它有几个典型问题。

### 第一，TTL 是 key 级别，不是 field 级别

Redis 的过期时间是作用在整个 key 上的，不是作用在 Hash 的某个 field 上。

也就是说：

```text
EXPIRE user:profile:1001 3600
```

会让整个用户 Hash 过期，而不是让某个字段过期。

如果你需要字段级过期，比如不同 token 不同过期时间，就不适合放在同一个 Hash 里。

不推荐：

```text
HSET user:token:1001 tokenA valueA
HSET user:token:1001 tokenB valueB
```

如果 tokenA 和 tokenB 过期时间不同，更推荐：

```text
SET user:token:1001:tokenA valueA EX 3600
SET user:token:1001:tokenB valueB EX 7200
```

### 第二，大 Hash 会形成大 key

如果一个 Hash 有几十万甚至上百万个 field，它就是大 key。

例如：

```text
HSET user:all:profile user1001 {...}
HSET user:all:profile user1002 {...}
HSET user:all:profile user1003 {...}
```

把所有用户资料塞进一个 Hash 是非常危险的。

正确方式是按实体拆 key：

```text
user:profile:1001
user:profile:1002
user:profile:1003
```

### 第三，不适合复杂嵌套对象

Hash 更适合扁平字段。

如果对象结构很复杂，比如：

```text
商品详情
  - 基础信息
  - 图片列表
  - SKU 列表
  - 促销规则
  - 店铺信息
  - 推荐标签
```

这种复杂聚合对象更适合 String JSON，而不是强行拆成 Hash。

---

## 6. String JSON vs Hash 选型结论

可以用下面这个表判断：

| 判断维度     | String JSON | Hash        |
| -------- | ----------- | ----------- |
| 读取方式     | 整对象读取       | 字段级读取       |
| 更新方式     | 整对象更新       | 字段级更新       |
| 对象结构     | 复杂嵌套对象      | 扁平对象        |
| 序列化成本    | 应用侧承担       | 较低          |
| 并发字段更新   | 容易覆盖        | 更自然         |
| TTL 粒度   | 整个 key      | 整个 key      |
| 大 key 风险 | 大 JSON      | field 过多    |
| 适合场景     | 接口缓存、聚合缓存   | 状态、资料、购物车字段 |

一句话总结：

```text
整对象读多，用 String JSON；
字段级读写多，用 Hash；
字段需要独立过期，拆成多个 String key；
对象特别大，先考虑是否应该放 Redis。
```

---

## 7. 源码视角：String 和 Hash 的底层差异

Redis 的 String 底层依赖 SDS，也就是 Simple Dynamic String。

SDS 的特点：

```text
1. 二进制安全
2. O(1) 获取长度
3. 减少内存重新分配
4. 不依赖 \0 判断字符串结束
```

这使得 String 可以存普通字符串，也可以存 JSON、二进制序列化数据。

Hash 则根据数据规模选择不同编码：

```text
小 Hash：listpack，节省内存
大 Hash：hashtable，提升查询效率
```

这体现了 Redis 的典型设计思想：

```text
小对象优先节省内存；
大对象优先保证访问性能。
```

源码上可以重点看：

```text
src/t_string.c
src/t_hash.c
src/sds.c
src/listpack.c
src/dict.c
src/object.c
```

# 二、ZSet：排行榜和延迟队列

Sorted Set，也叫 ZSet，是 Redis 中最有业务价值的数据结构之一。

它的模型是：

```text
member + score
```

其中 member 唯一，score 用于排序。

---

## 1. ZSet 为什么适合排行榜？

排行榜的核心需求通常有四个：

```text
1. 更新用户分数
2. 查询 Top N
3. 查询某个用户排名
4. 查询某个用户分数
```

ZSet 天然支持这些需求。

例如游戏排行榜：

```text
ZADD rank:game:1001 100 userA
ZADD rank:game:1001 200 userB
ZINCRBY rank:game:1001 50 userA
ZREVRANGE rank:game:1001 0 9 WITHSCORES
ZREVRANK rank:game:1001 userA
ZSCORE rank:game:1001 userA
```

### 常见排行榜场景

```text
游戏积分榜
直播贡献榜
文章热度榜
商品销量榜
用户活跃榜
粉丝榜
学习打卡榜
运动步数榜
```

### 为什么不用 MySQL 做实时榜？

MySQL 当然可以做排行榜，但高频实时榜会遇到几个问题：

```text
1. 高频 UPDATE 分数
2. 高频 ORDER BY
3. 索引维护成本高
4. Top N 查询压力大
5. 热门榜单容易形成热点行或热点索引页
```

Redis ZSet 更适合实时排名。

---

## 2. 排行榜 key 怎么设计？

不要把所有排行榜都塞进一个 key。

推荐按业务、周期、维度拆分：

```text
rank:game:{gameId}:daily:{yyyyMMdd}
rank:game:{gameId}:weekly:{yyyyWW}
rank:live:{roomId}:contribution:{yyyyMMdd}
rank:article:hot:{yyyyMMdd}
```

例如：

```text
rank:game:1001:daily:20260603
rank:game:1001:weekly:2026W23
rank:game:1001:monthly:202606
```

这样做有几个好处：

```text
1. 控制单个 ZSet 大小
2. 便于设置 TTL
3. 便于历史归档
4. 避免永久榜无限膨胀
5. 可以按周期做榜单结算
```

---

## 3. 排行榜工程实践

### 只保留 Top N

很多榜单并不需要保留所有用户。

例如只展示 Top 1000，可以定期裁剪：

```text
ZREMRANGEBYRANK rank:game:1001:daily:20260603 0 -1001
```

如果是倒序榜，需要注意裁剪方向，避免删错。

### 冷热分离

实时榜放 Redis，历史榜落库。

典型流程：

```text
用户行为产生分数
  -> ZINCRBY 更新 Redis 实时榜
  -> 定时任务结算榜单
  -> Top N 写入 MySQL / ClickHouse / 对象存储
  -> Redis 设置 TTL 或清理
```

### 避免全量读取

不要在线执行：

```text
ZRANGE rank 0 -1 WITHSCORES
```

大榜单全量读取会导致 Redis 主线程阻塞、网络响应变大、客户端内存上涨。

推荐分页：

```text
ZREVRANGE rank:game:1001:daily:20260603 0 99 WITHSCORES
ZREVRANGE rank:game:1001:daily:20260603 100 199 WITHSCORES
```

---

## 4. ZSet 实现延迟队列

ZSet 的另一个经典用途是延迟队列。

设计方式：

```text
key = delay:queue:{biz}
member = taskId 或 taskPayload
score = 任务执行时间戳
```

添加延迟任务：

```text
ZADD delay:order:cancel 1717392000 orderId:1001
```

消费者轮询到期任务：

```text
ZRANGEBYSCORE delay:order:cancel 0 当前时间戳 LIMIT 0 10
```

删除任务：

```text
ZREM delay:order:cancel orderId:1001
```

典型场景：

```text
订单超时取消
支付超时关闭
优惠券到期提醒
异步重试
定时通知
库存回滚
```

---

## 5. ZSet 延迟队列的原子性问题

普通实现有竞态问题。

例如多个消费者同时执行：

```text
ZRANGEBYSCORE delay:queue 0 now LIMIT 0 1
ZREM delay:queue task1
```

可能多个消费者都读到 task1，然后重复执行。

解决方式是用 Lua 脚本把“读取 + 删除”合成一个原子操作：

```lua
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
for i, task in ipairs(tasks) do
    redis.call('ZREM', KEYS[1], task)
end
return tasks
```

这样可以避免多个消费者同时取到同一个任务。

---

## 6. ZSet 延迟队列的边界

ZSet 延迟队列适合轻量任务，但不是强可靠 MQ。

需要自己处理：

```text
1. 消费失败重试
2. 任务执行超时
3. 消费者宕机
4. 死信队列
5. 幂等执行
6. 队列堆积
7. 任务体过大
```

更稳妥的设计是：

```text
ZSet 只存 taskId；
任务详情放数据库；
消费时根据 taskId 查详情；
任务执行状态由数据库记录。
```

这样即使 Redis 数据丢失，也可以通过数据库补偿扫描恢复。

---

## 7. 源码视角：ZSet 为什么强？

ZSet 底层通常由两类结构支撑：

```text
dict：根据 member 快速定位 score
skiplist：根据 score 维护有序关系
```

因此它能同时支持：

```text
按 member 查分数
按 score 排序
按排名查询
按分数范围查询
更新分数后调整排名
```

小 ZSet 可能使用 listpack 节省内存，规模变大后切换到 skiplist 编码。

源码重点看：

```text
src/t_zset.c
src/dict.c
src/listpack.c
```

# 三、Stream：消费者组机制怎么理解？

Redis Stream 是 Redis 5 引入的数据结构，适合做轻量消息流。

它比 List 更接近消息队列，因为它支持：

```text
1. 消息 ID
2. 消费者组
3. ACK 确认
4. Pending 消息
5. 消费失败后的转移
6. 历史消息读取
```

---

## 1. Stream 的基本模型

一条 Stream 消息长这样：

```text
消息 ID -> field-value 列表
```

写入消息：

```text
XADD order:events * orderId 1001 status created
```

其中 `*` 表示 Redis 自动生成消息 ID。

消息 ID 通常类似：

```text
1717392000000-0
```

前半部分是毫秒时间戳，后半部分是序号。

---

## 2. 普通读取：XREAD

普通读取方式：

```text
XREAD COUNT 10 BLOCK 5000 STREAMS order:events $
```

含义是从最新位置开始阻塞读取新消息。

这种模式适合简单订阅，但不适合多消费者协同，因为每个消费者都可能读到同样的消息。

---

## 3. 消费者组：Consumer Group

消费者组解决的是：

```text
多个消费者共同消费一个 Stream，每条消息只分配给组内一个消费者。
```

创建消费者组：

```text
XGROUP CREATE order:events order_group $ MKSTREAM
```

消费消息：

```text
XREADGROUP GROUP order_group consumer_1 COUNT 10 BLOCK 5000 STREAMS order:events >
```

其中 `>` 表示读取从未投递给其他消费者的新消息。

消费成功后确认：

```text
XACK order:events order_group messageId
```

---

## 4. Pending Entries List：PEL

Stream 消费者组里有一个非常重要的概念：PEL。

当消费者通过 `XREADGROUP` 读到消息后，但还没有 `XACK`，这条消息就会进入 Pending 状态。

也就是说：

```text
消息已经投递给某个消费者；
但 Redis 还不知道它是否处理成功。
```

如果消费者处理完成，调用：

```text
XACK order:events order_group messageId
```

Redis 就会把这条消息从 PEL 中移除。

如果消费者宕机，消息会一直留在 PEL 中。

---

## 5. 消费失败怎么处理？

可以用：

```text
XPENDING order:events order_group
```

查看 Pending 消息情况。

可以用：

```text
XAUTOCLAIM order:events order_group consumer_2 60000 0-0 COUNT 10
```

把空闲超过 60 秒的 Pending 消息转移给 consumer_2 重新处理。

这就是 Stream 实现失败恢复的关键机制。

---

## 6. Stream 消费者组实践模型

一个比较完整的消费流程：

```text
1. XGROUP CREATE 创建消费者组
2. XADD 写入消息
3. XREADGROUP 读取新消息
4. 业务处理
5. 处理成功后 XACK
6. 定时 XPENDING 扫描积压
7. XAUTOCLAIM 转移超时消息
8. 多次失败进入死信队列
```

死信队列可以单独设计：

```text
XADD order:events:dead * orderId 1001 reason timeout
```

---

## 7. Stream vs Kafka / RocketMQ

Stream 适合轻量消息，不适合替代所有 MQ。

适合 Stream 的场景：

```text
业务内部轻量异步
低延迟事件流
小中规模任务队列
Redis 已经是基础设施
消息保留时间较短
消费者组逻辑不复杂
```

更适合 Kafka / RocketMQ 的场景：

```text
公司级消息总线
跨业务域解耦
超大规模消息堆积
长时间消息保留
复杂重放
严格审计
高可靠异步链路
```

架构判断：

```text
业务内轻量事件：Redis Stream；
平台级消息系统：Kafka / RocketMQ。
```

---

## 8. Stream 生产避坑

### 第一，必须控制长度

如果一直 XADD，不裁剪，Stream 会无限增长。

推荐：

```text
XADD order:events MAXLEN ~ 100000 * orderId 1001 status created
```

`MAXLEN ~` 是近似裁剪，性能通常更好。

### 第二，必须监控 Pending

如果消费者读了消息但没有 ACK，PEL 会持续增长。

需要监控：

```text
XPENDING
消费者数量
Pending 数量
最老 Pending 消息时间
消息堆积长度
```

### 第三，消息体不要太大

Stream 应该存事件，不应该存大对象。

推荐：

```text
XADD order:events * orderId 1001 eventType created
```

不推荐：

```text
XADD order:events * fullOrderJson '{几十 KB 的大 JSON}'
```

大对象应该放数据库或对象存储，Stream 里只放 ID 和必要字段。

---

## 9. 源码视角：Stream 的底层结构

Stream 底层主要依赖：

```text
rax：radix tree，用于按消息 ID 索引
listpack：紧凑存储消息内容
consumer group 结构：维护消费组状态
PEL：维护已投递未确认消息
```

源码重点看：

```text
src/t_stream.c
src/rax.c
src/listpack.c
```

Stream 的设计可以理解为：

```text
用 radix tree 组织有序消息；
用 listpack 降低消息存储成本；
用 PEL 支撑消费者组可靠消费。
```

---

# 四、Bitmap：签到和活跃统计

Bitmap 本质上不是独立 Redis 对象类型，而是基于 String 的位操作。

它适合存储二值状态：

```text
0 / 1
是 / 否
签到 / 未签到
活跃 / 不活跃
完成 / 未完成
```

---

## 1. 用户签到模型

假设统计用户某月签到。

key 设计：

```text
sign:user:{userId}:{yyyyMM}
```

6 月 3 日签到：

```text
SETBIT sign:user:1001:202606 2 1
```

因为 offset 从 0 开始，所以 6 月 3 日对应 offset = 2。

查询某天是否签到：

```text
GETBIT sign:user:1001:202606 2
```

统计本月签到天数：

```text
BITCOUNT sign:user:1001:202606
```

这个模型非常省内存。

一个月最多 31 bit，几乎可以忽略不计。

---

## 2. 活跃用户统计模型

如果要统计每天活跃用户，可以设计：

```text
active:daily:{yyyyMMdd}
```

用户 1001 在 2026-06-03 活跃：

```text
SETBIT active:daily:20260603 1001 1
```

统计当天 DAU：

```text
BITCOUNT active:daily:20260603
```

计算两天都活跃的用户数：

```text
BITOP AND active:both:20260602_20260603 active:daily:20260602 active:daily:20260603
BITCOUNT active:both:20260602_20260603
```

计算两天任意一天活跃的用户数：

```text
BITOP OR active:any:20260602_20260603 active:daily:20260602 active:daily:20260603
BITCOUNT active:any:20260602_20260603
```

---

## 3. Bitmap 的优势

Bitmap 最大优势是内存极省。

如果用户 ID 最大是 1 亿，那么一天活跃状态需要：

```text
100,000,000 bit = 12.5 MB
```

如果用 Set 存活跃用户 ID，内存通常会大得多。

Bitmap 适合：

```text
用户签到
每日活跃
功能是否开启
任务是否完成
消息是否已读
用户是否在线
AB 实验命中状态
```

---

## 4. Bitmap 的限制

Bitmap 最大限制是 offset。

如果用户 ID 很稀疏，就会浪费内存。

例如：

```text
最大用户 ID = 10,000,000,000
实际用户数 = 1,000,000
```

如果直接用用户 ID 做 offset，Bitmap 会被撑得很大。

解决方式：

```text
1. 用户 ID 映射为连续内部 ID
2. 按用户 ID 分桶
3. 改用 Set 或 HyperLogLog
4. 改用离线数仓统计
```

分桶示例：

```text
active:daily:20260603:bucket:0
active:daily:20260603:bucket:1
active:daily:20260603:bucket:2
```

offset 使用桶内偏移。

---

## 5. Bitmap 生产避坑

危险操作：

```text
SETBIT key 超大 offset
BITCOUNT 超大 bitmap 高频执行
BITOP 多个大 bitmap 高频计算
```

建议：

```text
1. 控制 offset 范围
2. 按天/月拆 key
3. 大规模 BITOP 放到异步任务
4. 统计结果缓存起来
5. 对 bitmap 设置 TTL 或定期归档
```

Bitmap 适合在线实时粗统计，但复杂分析仍然建议放到数仓或 OLAP。

---

# 五、HyperLogLog：UV 估算

HyperLogLog 是一种概率统计结构，用于估算不重复元素数量。

Redis 中常用命令：

```text
PFADD key element
PFCOUNT key
PFMERGE dest key1 key2
```

---

## 1. UV 统计模型

统计文章 UV：

```text
PFADD article:1001:uv user1001
PFADD article:1001:uv user1002
PFCOUNT article:1001:uv
```

统计站点每日 UV：

```text
PFADD site:uv:20260603 user1001
PFADD site:uv:20260603 user1002
PFCOUNT site:uv:20260603
```

合并一周 UV：

```text
PFMERGE site:uv:2026W23 site:uv:20260601 site:uv:20260602 site:uv:20260603
PFCOUNT site:uv:2026W23
```

---

## 2. HyperLogLog 适合什么？

适合只关心“去重数量”的场景。

典型场景：

```text
页面 UV
站点 UV
独立 IP 数
搜索词去重数
广告曝光去重估算
接口独立调用用户数
设备去重数量
```

它的优势是：

```text
内存占用非常小；
可以统计非常大的去重集合；
支持多个 HLL 合并。
```

---

## 3. HyperLogLog 不适合什么？

HyperLogLog 是估算，不是精确集合。

它不适合：

```text
1. 判断某个用户是否访问过
2. 获取访问用户列表
3. 精确活动参与人数
4. 财务计数
5. 库存计数
6. 强审计统计
7. 需要 100% 准确的报表
```

例如，不能用它判断：

```text
用户 1001 是否访问过文章 1001？
```

因为 HyperLogLog 不保存成员明细。

如果需要精确判断，用 Set。

如果只需要大盘趋势，用 HyperLogLog。

---

## 4. HyperLogLog vs Set vs Bitmap

| 场景                 | 推荐结构        |
| ------------------ | ----------- |
| 需要精确去重，并且要判断成员是否存在 | Set         |
| 只需要估算去重数量          | HyperLogLog |
| 二值状态，ID 连续或可映射     | Bitmap      |
| 需要离线精确统计和复杂分析      | 数仓 / OLAP   |

举例：

```text
活动报名人数必须精确：Set 或数据库
页面 UV 大盘趋势：HyperLogLog
每日活跃状态：Bitmap
最终经营报表：数仓
```

---

## 5. 生产组合方案

大厂里常见组合是：

```text
实时趋势：HyperLogLog
实时精确小集合：Set
实时二值状态：Bitmap
离线最终口径：Flink / Hive / ClickHouse
```

例如 UV 统计：

```text
用户访问页面
  -> Redis HyperLogLog 实时估算
  -> 日志进入 Kafka
  -> Flink / Hive 离线精确计算
  -> 报表以离线结果为准
```

这样既保证实时性，又保证最终报表准确性。

---

# 六、大 key 治理规范

大 key 是 Redis 生产环境最常见、也最危险的问题之一。

注意，大 key 不是 key 名字长，而是 value 太大。

---

## 1. 什么是大 key？

典型大 key：

```text
一个 String 几 MB 或几十 MB
一个 Hash 有几十万个 field
一个 Set 有几百万个 member
一个 ZSet 有几百万个 member
一个 Stream 长期不裁剪
一个 Bitmap offset 极大
```

大 key 的本质是：

```text
一个 Redis key 背后挂载了过多数据。
```

---

## 2. 大 key 有什么危害？

大 key 会带来：

```text
1. 读取慢
2. 删除慢
3. 网络传输大
4. 主线程阻塞
5. AOF / RDB 变大
6. 主从同步变慢
7. Cluster 分片不均
8. 内存倾斜
9. 客户端超时
```

例如：

```text
HGETALL huge:hash
SMEMBERS huge:set
ZRANGE huge:zset 0 -1
DEL huge:key
```

这些操作都可能阻塞 Redis 主线程。

---

## 3. 大 key 怎么发现？

常见手段：

```text
redis-cli --bigkeys
SCAN + MEMORY USAGE
业务侧 key 采样
监控平台 Top Key
云厂商 Redis 诊断工具
```

命令示例：

```text
redis-cli --bigkeys
MEMORY USAGE user:profile:1001
```

如果是集群，需要每个分片都扫描。

---

## 4. 大 key 怎么治理？

### String 大对象

问题：

```text
SET product:detail:1001 巨大 JSON
```

治理：

```text
1. 拆分冷热字段
2. 大字段放对象存储
3. Redis 只存摘要
4. 压缩 JSON
5. 控制单 value 大小
```

### Hash 大对象

问题：

```text
一个 Hash 存所有用户
```

治理：

```text
按用户拆 key
按业务维度拆 key
限制 field 数量
避免 HGETALL
使用 HSCAN 分批处理
```

### Set / ZSet 大集合

治理：

```text
按时间拆分
按业务分桶
只保留 Top N
冷数据落库
使用 SSCAN / ZSCAN
避免全量读取
```

### Stream 大队列

治理：

```text
MAXLEN 裁剪
按业务拆 stream
消费失败告警
定期清理历史消息
监控 Pending
```

### 删除大 key

不要直接：

```text
DEL huge:key
```

推荐：

```text
UNLINK huge:key
```

`UNLINK` 会异步释放内存，降低主线程阻塞风险。

---

# 七、热 key 治理规范

热 key 是另一个高频问题。

大 key 是“数据大”，热 key 是“访问频率高”。

一个 key 不大，也可能是热 key。

---

## 1. 什么是热 key？

热 key 是指某个 key 承担了远高于其他 key 的请求量。

例如：

```text
热门商品详情
首页配置
秒杀库存
直播间状态
热门文章
明星活动页
全局开关
热门排行榜
```

在 Redis Cluster 中，同一个 key 只会落到一个 slot、一个分片上。

所以即使整个集群很大，一个热 key 也可能打爆单个分片。

---

## 2. 热 key 有什么危害？

```text
1. 单分片 CPU 飙高
2. 单分片网络打满
3. 请求排队
4. P99 延迟上升
5. 连接池耗尽
6. 业务超时重试
7. 重试进一步放大流量
```

热 key 最危险的是会引发雪崩式放大：

```text
Redis 慢
  -> 应用超时
  -> 应用重试
  -> 请求更多
  -> Redis 更慢
```

---

## 3. 热 key 怎么发现？

常见方式：

```text
redis-cli --hotkeys
客户端埋点统计 key 访问频率
代理层统计
云厂商 hotkey 诊断
业务日志采样
Redis 命令统计
```

生产中更推荐在客户端或代理层做 key 维度采样，因为 Redis 自身不一定能低成本记录所有 key 的访问频率。

---

## 4. 热 key 怎么治理？

### 第一，本地缓存

对于读多写少的热点数据，可以放到应用本地缓存。

例如：

```text
Redis -> 应用本地 Caffeine / Guava Cache -> 业务请求
```

适合：

```text
首页配置
热门商品详情
全局开关
地区配置
字典表
```

注意：

```text
本地缓存要控制 TTL；
配置类数据要有主动刷新或版本号机制。
```

### 第二，多级缓存

典型链路：

```text
本地缓存
  -> Redis
  -> 数据库
```

甚至可以加 CDN：

```text
CDN
  -> 网关缓存
  -> 应用本地缓存
  -> Redis
  -> DB
```

### 第三，请求合并

如果缓存失效瞬间大量请求打进来，不要让每个请求都去重建缓存。

可以用 singleflight 思路：

```text
同一个 key 同一时刻只有一个线程重建缓存；
其他线程等待结果或返回旧值。
```

### 第四，热点 key 拆分

对于某些可以拆分的热点 key，可以做副本 key：

```text
product:detail:1001:copy:0
product:detail:1001:copy:1
product:detail:1001:copy:2
product:detail:1001:copy:3
```

读取时随机访问一个副本。

写入时更新所有副本，或通过异步任务同步。

适合读多写少场景。

### 第五，限流降级

热点 key 如果来自突发流量，比如秒杀活动，必须配合限流。

```text
网关限流
用户维度限流
接口维度限流
热点商品维度限流
排队削峰
降级兜底
```

Redis 不是抗所有流量的最后防线。

---

# 八、大 key 和热 key 的区别

| 维度    | 大 key                | 热 key           |
| ----- | -------------------- | --------------- |
| 核心问题  | value 太大             | 访问太频繁           |
| 主要风险  | 阻塞、内存倾斜、传输慢          | 单分片过载、延迟升高      |
| 典型命令  | HGETALL、SMEMBERS、DEL | GET、HGET、ZSCORE |
| 是否一定大 | 是                    | 不一定             |
| 是否一定热 | 不一定                  | 是               |
| 治理方式  | 拆 key、分页、UNLINK      | 本地缓存、多副本、限流     |

一句话：

```text
大 key 是容量问题；
热 key 是流量问题。
```

但两者可能叠加。

最危险的是：

```text
又大又热的 key。
```

例如：

```text
一个热门商品详情 JSON 很大，同时每秒被访问几万次。
```

这种 key 必须重点治理。

---

# 九、完整 Redis 建模方法论

Redis 建模可以按以下流程判断。

## 1. 先判断访问模式

```text
整对象读写：String JSON
字段级读写：Hash
去重判断：Set
排序排名：ZSet
事件消息：Stream
二值状态：Bitmap
去重数量估算：HyperLogLog
```

## 2. 再判断数据规模

```text
单 value 是否过大？
集合元素是否过多？
是否会无限增长？
是否需要按时间拆 key？
是否需要 Top N 裁剪？
```

## 3. 再判断一致性要求

```text
是否允许丢？
是否需要精确？
是否需要最终落库？
是否需要幂等？
是否需要补偿？
```

## 4. 再判断访问热点

```text
是否可能成为热点 key？
是否需要本地缓存？
是否需要副本 key？
是否需要限流？
是否需要逻辑过期？
```

## 5. 最后判断运维治理

```text
是否有 TTL？
是否有监控？
是否能扫描？
是否能删除？
是否能降级？
是否有容量上限？
```

# 十、面试表达总结

如果面试官问：“Redis 对象缓存用 String 还是 Hash？”

可以这样回答：

> 如果是整对象读取，比如商品详情、文章详情、接口聚合结果，用 String 存 JSON 更简单；如果经常字段级读写，比如用户状态、购物车、设备状态，用 Hash 更合适。Hash 可以避免整对象序列化和反序列化，但要注意 TTL 是 key 级别，不是 field 级别，也要避免 field 过多形成大 key。

如果面试官问：“ZSet 为什么适合排行榜？”

可以这样回答：

> ZSet 的 member 唯一，score 用于排序，适合更新分数、查询 Top N、查询排名和查询分数。底层通常通过 dict 快速定位 member，通过 skiplist 维护 score 顺序，所以适合实时排行榜。生产中要按业务和周期拆 key，只保留 Top N，历史榜单落库，避免一个永久大榜无限膨胀。

如果面试官问：“ZSet 延迟队列有什么问题？”

可以这样回答：

> ZSet 延迟队列通常用 score 存执行时间戳，消费者通过 ZRANGEBYSCORE 拉取到期任务。但读取和删除不是天然原子，多消费者可能重复取任务，需要 Lua 脚本保证原子性。同时它缺少完整 MQ 的 ACK、重试、死信和堆积治理能力，所以适合轻量延迟任务，不适合强可靠消息场景。

如果面试官问：“Redis Stream 消费者组怎么保证消息不丢？”

可以这样回答：

> Stream 消费者组通过 XREADGROUP 投递消息，消费者处理成功后用 XACK 确认。未 ACK 的消息会进入 PEL，也就是 Pending Entries List。如果消费者宕机，可以通过 XPENDING 查看积压，再用 XAUTOCLAIM 把超时未确认的消息转移给其他消费者处理。但业务仍然要保证幂等、重试和死信队列。

如果面试官问：“Bitmap 和 HyperLogLog 怎么选？”

可以这样回答：

> Bitmap 适合二值状态，比如签到、活跃、是否完成任务，优点是精确且支持位运算，但依赖 offset 范围，ID 稀疏会浪费内存。HyperLogLog 适合 UV 这类大规模去重数量估算，内存小，但有误差，不能获取成员，也不能判断某个用户是否存在。需要精确成员就用 Set，只要估算数量就用 HyperLogLog。

如果面试官问：“大 key 和热 key 怎么治理？”

可以这样回答：

> 大 key 是 value 太大，风险是阻塞、传输慢、内存倾斜和删除慢，治理方式是拆 key、分页、限制集合长度、用 UNLINK 异步删除。热 key 是访问频率过高，风险是单分片过载和延迟飙升，治理方式是本地缓存、多级缓存、请求合并、热点副本、限流降级。大 key 是容量问题，热 key 是流量问题，两者都要在建模阶段提前规避。

---

# 十一、结语

Redis 的高级使用，不是会写更多命令，而是能在不同业务模型之间做取舍。

可以总结成几句话：

```text
对象缓存：整对象用 String JSON，字段级用 Hash；
实时排名：用 ZSet，但要按周期拆榜、控制 Top N；
轻量延迟任务：可以用 ZSet，但要 Lua 保证原子取删；
轻量消息流：用 Stream，但要处理 ACK、Pending、重试和死信；
二值状态统计：用 Bitmap，但要控制 offset 和 key 粒度；
UV 估算：用 HyperLogLog，但不要用于精确场景；
大 key：提前拆，避免全量读写；
热 key：用本地缓存、多副本和限流治理。
```

Redis 的性能优势来自内存和数据结构，但 Redis 的稳定性来自建模和治理。

真正成熟的 Redis 使用方式，不是“什么都往 Redis 里塞”，而是：

```text
知道什么适合放 Redis；
知道怎么放；
知道什么时候不能放；
知道数据变大和流量变热之后怎么兜底。
```

这才是开发和架构视角下真正有价值的 Redis 实战能力。
